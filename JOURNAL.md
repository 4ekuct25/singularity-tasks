# Журнал решений

## 2026-09-11 — перехват задачи: один PATCH вместо двух, подтверждение с паузой

**Что:** `scripts/sing.py` — введена `set_task_tags()`, `drop_task_tag`/`add_task_tag`
стали её обёртками; `claim_task` при `--take-over` снимает чужую метку и ставит свою
**одним** PATCH; подтверждение перечитывается с паузой (`TAG_SETTLE_TRIES=4`,
`TAG_SETTLE_PAUSE=1` с). Новый `tools/check-tag-lag.py` (нагрузка + контрольный прогон
против старой реализации через `--sing`), `tests/test_claim.py`. Карточка `T-fc3a3096`.
Разбор и код — субагент `agent:claude-takeover`; его убил лимит сессии API ровно на этапе
воспроизведения нагрузки, перенос и проверку довёл координатор.

**Почему:** два PATCH подряд (`tags=[]`, потом `tags=[мой]`) оставляли окно, в котором у
задачи нет ни одной agent-метки — она выглядит свободной, хотя её берут. Если второй PATCH
не подтверждался, она такой и оставалась: исход **хуже честного отказа**. Поле `tags`
перезаписывается целиком, поэтому окна можно не иметь вовсе — сервер либо применит новый
список, либо не применит ничего. Отсюда же ответ на «что делать с уже снятой чужой меткой»:
возвращать нечего, компенсация была бы вторым запросом, который тоже может не дойти.

**Почему повтора записи здесь нет:** запись не теряется, а **отстаёт**. Повторный PATCH
переписал бы встречный захват и сломал правило «победитель ровно один»: затёртая метка
обязана остаться затёртой, иначе оба агента решат, что задача их. Повторяется только
чтение-подтверждение.

**Как проверено:** контрольный прогон под нагрузкой (3 писателя, 54 шумовые записи), одна
и та же фикстура для обеих реализаций. **Старый код: перехватов 2 из 3, одна задача
осталась без agent-метки** — «ДЕФЕКТ ВОСПРОИЗВЕДЁН». **Новый: 3 из 3, без меток 0.**
Гонка не сломана: `tools/check-claim-race.py` трижды подряд и `-n 4` — ровно один захват.
`tests/run.py fast` — 62 из 62.

**Наблюдение (общее правило, не про этот баг):** одно чтение не способно отличить «сервер
ещё не применил» от «сервер не применил» — оно одинаково видит старое. Различает их только
время. Эта же болячка уже лечилась в `tools/zz-project.py` после `DELETE`; теперь она
названа явно, потому что встречается всюду, где после записи идёт немедленная сверка.

**Грабли моего собственного слияния:** я скопировал файлы из worktree агента целиком —
и снёс ими `board_layout()` и правки про доску «Сегодня», слитые часом раньше. Поймал
набор тестов (`AttributeError: no attribute 'board_layout'`), а не вычитка диффа. Ветки,
отошедшие от разных баз, переносить надо по функциям, а не файлами.

**Откат:** `git revert 7eb1073`.

## 2026-09-11 — связка задачи выбирается по доске её проекта, а не первая попавшаяся

**Что:** `scripts/sing.py` — добавлены `task_project()`, `project_status_ids()` (с памяткой;
системные колонки учитываются по детерминированному id) и `board_links()`; `task_column()`
и `move_to_column()` получили `project_id` и берут связку **только своей доски**. Новый
`tools/check-today-link.py` (`--stub` / `--live`). Карточка `T-ee0289ed`. Сделано субагентом
`agent:claude-todaycol`, перенесено мной вручную.

**Почему:** у задачи бывает больше одной канбан-связки. Кроме колонки своего проекта есть
системная доска «Сегодня» — псевдопроект `P-TODAY` со своими колонками и связкой
`KTS-<taskId>-TODAY`. `live[0]` не проверял, чьей колонке принадлежит связка, поэтому
`task_column()` мог вернуть чужую колонку, а `move_to_column()` PATCH-ем переводил связку
«Сегодня» на колонку проекта — то есть **снимал задачу с доски «Сегодня» пользователя**.
Это порча живых данных, а не косметика.

**Как проверено:** на живом API на колонках `P-TODAY` в моменте висело 24 связки
`KTS-…-TODAY`, и три выборочные задачи из них лежат в обычных проектах, имея **единственную**
связку с `P-TODAY` — на них старый код возвращал чужую колонку гарантированно.
`tools/check-today-link.py --stub`: до правки провалено 7 проверок из 8 (PATCH уходил в
`KTS-<T>-TODAY`), после — 8 из 8, на собранном дереве тоже 8 из 8. Доска «Сегодня» после
работы: 13/7/3 связки — как до.

**Почему переносил руками, а не сливал:** ветка субагента отошла от старого `main`, где не
было ни повторов в `move_to_column`, ни параметра `fatal`, ни `tests/`. Слияние затёрло бы
их его версией. Перенесены только новые функции, мой `move_to_column` научен фильтровать.

**Что вскрылось при переносе (и было починено):** наивный перенос добавлял `GET /task` на
**каждый** вызов — в цикле повторов это 7 запросов вместо 3. Поймал набор тестов, а не
чтение диффа: он считает запросы, а не только результат. Проект теперь передаётся от
вызывающих, где он уже известен из конфига.

**Наблюдение по API:** `POST /v2/kanban-task-status` не принимает поле `id` и выводит его из
`taskId` — повторный POST **апсертит** `KTS-<taskId>`, а не заводит вторую связку. Значит,
состояние «две связки сразу» через REST не создать: `-TODAY` заводит только приложение,
и этот случай проверяется заглушкой, а не живьём.

**Откат:** `git revert <хеш>`.

## 2026-09-11 — board: роль без колонки больше не подменяется задачами вне колонок

**Что:** `scripts/sing.py` — раскладка вынесена в чистую `board_layout()`; роль, которой нет
в `singularity.json`, получает пустой список вместо `by_col[None]` и печатается пометкой
**без счётчика** («— 0» читалось бы как «в колонке пусто»), плюс блок `⚠ РОЛЕЙ БЕЗ КОЛОНКИ`
сверху. `col_id()` называет фактический путь привязки вместо зашитого `.claude/`; `doctor`
различает `НЕТ В ПРИВЯЗКЕ` и `КОЛОНКА ПРОПАЛА В ТРЕКЕРЕ`. Карточка `T-278ad639`. Сделано
субагентом `agent:claude-phantom`, слито мной.

**Почему:** `cid = cfg["columns"].get(role)` на отсутствующей роли даёт `None`, а
`by_col[None]` — это задачи ВНЕ колонок. Доска печатала их под каждой непривязанной ролью:
показывала то, чего на доске нет, да ещё и дважды. Отказ был бы хуже пометки: `board` —
первая команда цикла и единственный способ увидеть доску именно тогда, когда привязка поехала.

**Как проверено:** черновой подпроект с привязкой без роли `review` и двумя задачами вне
колонок. ДО: `[review] ? — 2` с обеими чужими задачами. ПОСЛЕ: предупреждение про роль без
колонки, задач под ролью нет, а задача из живой колонки «На проверке» видна в «КОЛОНКИ МИМО
ПРИВЯЗКИ». A/B на полной привязке: старый и новый вывод `board` совпали **байт в байт** —
регрессии на здоровом конфиге нет. `tests/run.py fast` 57/57 (было 53, случай не ловился),
и тест проверен на способность краснеть.

**Наблюдение (дороже самого бага):** один и тот же сломанный конфиг читался тремя способами.
`board` молча подменял содержимое, `next`/`list` отказывали — да ещё сообщением про
`.claude/`, хотя привязка лежала в `.agents/`, — а `doctor` ставил диагноз «колонка пропала»
на колонку, которая цела. Асимметрия «пишущая команда отказывает, читающая помечает и
продолжает» оставлена намеренно и зафиксирована в docstring `col_id()`.

**Откат:** `git revert -m 1 <хеш слияния>`.

## 2026-09-11 — paged() отдавал первые 1000 объектов и молчал об этом

**Что:** `scripts/sing.py` — у `paged()` снят потолок `limit=1000` по умолчанию, offset
шагает по **запрошенному окну** (а не по числу отданных строк), выход — по пустой
странице (а не по `offset >= total`), недобор против `total` печатается в stderr,
добавлен предохранитель от вечного цикла. Новый `tools/paging-loadtest.py`. Карточка
`T-bcfd2bda`. Сделано субагентом `agent:claude-paging`, слито мной.

**Почему:** на проекте в 1150 задач `paged()` возвращал ровно 1000 и останавливался.
Хвост терялся молча: `board` показывал в колонке 1000 вместо 1150, `column_map` терял
150 связок, и 150 задач пропадали с доски **совсем** — их не было ни в `live_tasks`, ни в
`column_map`, поэтому они не попадали даже в «вне колонок». Доска выглядела правдоподобной
и была неверной. Рядом ещё две мины: `total` сервер считает ДО post-фильтра (негодное
условие остановки), а шаг offset по `len(batch)` при post-фильтре двигает окно внахлёст.

**Как проверено:** живая фикстура 1150 задач и 1150 связок (эталонный скан и
`pagination.total` сходятся). До правки: `paged()` 1000/1150 — **87.0% полноты**, 145
номеров заголовков не вернулись, `column_map` 1000, `board` 1000. После: 1150/1150, дублей
0, `board` 850+300=1150 при раскладке по двум колонкам, `list` 1150 строк. Граница 200
была исправна и до правки (224 создано — 224 вернул). Набор заглушек прежнюю реализацию
проваливает 4 из 6, новую — 0 из 6.

**Наблюдение (почему предохранитель именно такой):** первая версия считала потолок по
числу СОБРАННЫХ объектов — при дедупликации счётчик перестаёт расти, и цикл становится
вечным. На живом API это не воспроизводилось; поймала заглушка. Гейт «сумма частей против
целого» тут не роскошь: без него замер даёт правдоподобную таблицу, из которой следует
неверный вывод.

**Откат:** `git revert -m 1 8a2d547`.

## 2026-09-11 — регрессионный набор tests/: дешёвое отдельно от дорогого

**Что:** `tests/` в корне — `run.py` с группами `fast` / `live` / `slow`, плюс
`test_pure.py`, `test_retry.py`, `test_live.py`. Заведение и снос чернового подпроекта
переехали в `tools/zz-project.py`, `check-claim-race.py` зовёт их вместо своей копии.
`tests/` намеренно **не** раскатывается: `install.sh` копирует явный список
(`SKILL.md README.md scripts references`). Карточка `T-c77a6d9a`. Сделано субагентом
`agent:claude-tests`, слито мной.

**Почему:** каждая правка `sing.py` проверялась руками. Отдельная причина не синхронизировать
`tests/` — живые тесты создают и удаляют проекты в трекере пользователя, и класть их в
автозагружаемый каталог скилла у пяти инструментов не стоит.

**Как проверено:** `fast` — 53 теста, 4.6 с, проходит **при пустом окружении**: переменные
сняты, `security` подменён всегда падающей заглушкой, файла-токена нет. `live` — 18 тестов,
118.7 с на черновом подпроекте. `slow` — 19/19 через существующий `tools/check-retry.py`
(на собранном дереве он теперь даёт 23 из 23). Набор умеет краснеть: `prio_of` → `or 1`
уронил 3 теста; 429 без повтора на POST — 1; `Retry-After` без разбора HTTP-даты — 1
(пауза 0.06 с вместо 2 с); `move_to_column` через `change-column` — 2 живых теста
(`todo→wip` прошёл, `wip→done` молча не применился). После каждого контроля `sing.py`
возвращался побайтно.

**Наблюдение (объясняет целый класс ложных отказов):** сервер принимает запись в очередь
синхронизации и **отвечает раньше, чем применит её**. Немедленный GET после PATCH/DELETE
отдаёт старое состояние, и всё, что судит по первому чтению, докладывает ложный отказ.
Зависимость от нагрузки замерена: на загруженной очереди (`number in queue` 7→15)
`start --take-over` падал 2 прогона из 2, на спокойной проходил с первого раза. Заведено
`T-fc3a3096`. Отсюда же правило для проверок: подтверждать снос не первым чтением, а с
паузой и повтором.

**Ещё факт:** `DELETE /tag/{id}` отвечает `500 Sync error` и через минуту, `PATCH
{"removed": true}` тоже не проходит — **тег удалить нечем**. Следствие: имена пробных
агентов обязаны быть фиксированными, иначе каждый прогон добавляет в общий на аккаунт
список новую строку навсегда. Мой же `tools/check-claim-race.py -n` уже намусорил
тегами `agent:zz-agent-0…3`, `agent:zz-first`, `agent:zz-second` — убрать их невозможно.

**Откат:** `git revert -m 1 <хеш слияния>`; `scripts/sing.py` правка не трогала.

## 2026-09-11 — девять карточек очереди сделаны параллельными субагентами

**Что:** очередь проекта `singularityapp` разобрана девятью субагентами, каждый в своём
git worktree и своей ветке, слияние — централизованно в этой ветке. Слито семь веток
(`T-c3070463` MCP, `T-672db7ad` Antigravity, `T-075e1847` read-timeout, `T-a249d129`
сверка эталона, `T-fb2b536b` чек-лист, `T-1c00aafb` дневник, `T-040c1e1f` форматы полей);
`T-bcfd2bda` (пагинация) и `T-c77a6d9a` (автотесты) в работе. Каждая запись по существу —
отдельным блоком ниже.

**Почему именно так:** параллельные агенты в одном рабочем дереве затирали бы друг друга,
а в worktree от общей базы конфликтуют только в тех же местах файла — это git решает.
Раскатку (`tools/install.sh`) и `JOURNAL.md` субагентам запретил намеренно: установщик
копирует каталог скилла целиком и увёз бы в общие каталоги пяти инструментов чужую ветку,
а журнал все пишут в начало файла — гарантированный конфликт на каждом слиянии.

**Как проверено:** после каждого слияния — `py_compile`, `tools/audit-secrets.sh`,
прогон затронутых проверок. На собранном дереве: `tools/check-retry.py` — **23 из 23**,
`doctor --write` — 6 из 6 (до того, как сервер начал штормить, см. ниже), `board` снова
показывает 16 закрытых задач вместо 0. Конфликтов было пять, все — содержательные
(два блока в одно место), разрешены сложением; ни одного случая, когда правки
противоречили бы друг другу.

**Чего это стоило и что пошло не так:**

1. ⚠️ **Агент удалил чужую фикстуру.** Убирая за собой, агент по дневнику снёс все `zz-`
   проекты аккаунта — включая `zz-paging` (133 задачи) работающего соседа. Виноват не он:
   в постановке каждому было написано «после прогона ни одного `zz-` проекта остаться не
   должно», и это прочиталось как разрешение. Правильная формулировка — «удали СВОЙ
   черновик по имени», а не «пусть не останется ни одного». Пострадавший предупреждён,
   замер пересняли.
2. ⚠️ **Сервер штормит под параллельной нагрузкой.** `429 ThrottlerException` — ожидаемо,
   он теперь повторяется. Но всплыл и второй режим: `500 Sync error: … number in queue 13`
   на `POST /task`. Запрос при этом **не применяется** (сверено `GET`-ом), а повторять
   `POST` на `5xx` нельзя — создаст дубль. Итог: под нагрузкой `doctor --write` дважды
   подряд упал и оставил пробную задачу на доске. Уборка честно сообщила
   `ПРОБА ОСТАЛАСЬ НА ДОСКЕ` — механизм сработал, но осадок в том, что девять агентов на
   один аккаунт трекер не держит. Практический вывод: параллелить по 3–4, не по 9.
3. **Волна 403 от API модели** положила семь агентов из девяти разом, большинство — на
   последнем шаге. Все возобновлены с сохранённым контекстом, работа не потеряна.

**Откат:** каждое слияние — отдельный merge-коммит, откатывается `git revert -m 1 <хеш>`.
Ветки субагентов сохранены (`worktree-agent-*`).

## 2026-09-11 — MCP-сервер оценён и отклонён

**Что:** решение не подключать `mcp.singularity-app.com`; CLI остаётся единственным путём.
Разбор с фактами — в `references/api.md`, формулировка в `SKILL.md` приведена в
соответствие, `tools/mcp-probe.py` повторяет проверку. Карточка `T-c3070463`. Сделано
субагентом `agent:claude-mcp`, слито мной (ветка `worktree-agent-a1e36dd11453fabc9`).

**Почему:** ограничение области «ИИ проекты» через MCP нечем удержать. Скоупы сервера
гранулярны по типу сущности (`tasks:write`, `kanban:write`), измерения «проект» в них нет,
а `toolsets` режет группы инструментов, а не данные. Токен открыл бы агенту весь аккаунт:
4 проекта в области против 41 вне неё. Сегодня барьер держит код (`assert_allowed` на
проекте самой задачи), через MCP остался бы только текст промпта — слабее переменной
окружения, которую в §3 правил намеренно не стали заводить.

**Как проверено:** REST-токен из Keychain → `401` на `initialize`; контрольный замер
заведомо мусорной строкой даёт **байт-в-байт тот же ответ**, при этом `doctor` на том же
токене зелёный — значит REST-токены не распознаются как класс, а не «не хватает прав».
Метаданные auth server: `grant_types_supported: ["authorization_code","refresh_token"]`,
device-flow и OIDC-discovery → 404, то есть headless/cron переавторизоваться не может.
Состав скоупов снят с `/.well-known/oauth-protected-resource` — 17 штук, project-скоупа
нет. `tools/list` снять не удалось: нужен тариф Pro/Elite и браузерный OAuth. На вывод не
влияет — оба решающих пункта следуют из метаданных авторизации и модели скоупов, а не из
состава инструментов.

**Откат:** н/п (решение и доки). Пересмотреть, если вендор добавит `client_credentials`
или device-flow **и** скоуп с ограничением по проекту — условие записано в `references/api.md`.

## 2026-09-11 — ретраи в request(): 429 и 5xx повторяются по-разному

**Что:** `scripts/sing.py`, `request()` и константы рядом с `NET_TIMEOUT`: `429`
повторяется для ЛЮБОГО метода (4 попытки), пауза — из `Retry-After` (число секунд или
HTTP-дата), без заголовка `1.5·n`; `5xx` — только `GET` (3 попытки); прочие `4xx` и `401`
— как было. Потолки `RETRY_AFTER_CAP=30` с на паузу и `RETRY_WAIT_BUDGET=90` с на запрос.
Заглушка — `tools/check-retry.py`. Карточка `T-bb8d9b41`. Сделано субагентом
`agent:claude-retry`, слито и перепроверено мной.

**Почему:** ключевое различие — не код, а класс отказа. На `429` сервер запрос **не
выполнил** (отказался обслужить), поэтому повтор безопасен даже для `POST` — иначе
троттлинг ронял бы цепочку `add` ровно там же, где её роняли тайм-ауты. На `5xx` запрос
мог примениться, и повтор `POST` создаст второй объект. Что троттлинг не теория,
подтвердилось в тот же день: под четырьмя параллельными агентами живой API отдал
`429 ThrottlerException`.

**Как проверено:** `tools/check-retry.py` на слитом дереве — **19 сценариев из 19**.
429 `Retry-After: 1` → 4 запроса, паузы 1.01×3, 3.02 с, exit 1; `Retry-After: 3600` при
потолке 2 → паузы 2.01×3; бюджет 2 с при `Retry-After 1.5` → 1.51+0.51, стоп на 2.01 с;
500 на GET → 3 запроса, 1.51+3.01 = 4.51 с; **500 на POST и PATCH → ровно 1 запрос,
0.00 с**; `soft=True` на 429 → 4 запроса и `None`, а 429→200 отдаёт данные, а не `None`;
успех без отказов → 1 запрос, 0 пауз.

**Наблюдение (почему код такой):** read-timeout **не** является `URLError`. urllib
заворачивает в `URLError` только обрыв/отказ соединения; сервер, который принял
соединение и молчит, роняет `getresponse()` голым `builtins.TimeoutError` мимо обоих
`except` — вместо сообщения виден traceback (замер: 2.00 с при `NET_TIMEOUT=2`). Заведена
`T-075e1847`, в этой правке не чинилось.

**Ловушка проверки:** HTTP-дату в `Retry-After` нельзя вычислять при сборке сценариев — к
своей очереди она протухает, пауза выходит нулевой, и сценарий «проходит», ничего не
измерив. Считать в момент прогона плюс контрольный сценарий с заведомо большой датой.

**Откат:** `git checkout -- scripts/sing.py references/api.md`, `rm tools/check-retry.py`.

**Что:** перенос задач по колонкам переведён с `POST /task/{id}/change-column` на
`PATCH /kanban-task-status/{link}` с обязательным перечитыванием состояния.
**Почему:** `change-column` на **системных** колонках проекта (`KS-<projectId>-TODO` и
компания) отвечает `200` и возвращает задачу, но связку не меняет. На пользовательских
колонках он работает — поэтому первый прогон, шедший по своим колонкам, ничего не выявил.
Из-за доверия к коду ответа одна задача осиротела при удалении колонки под ней.
**Как проверено:** перебором способов на живой задаче — `PATCH /task {kanbanStatusId}` не
сработал, `PATCH /kanban-task-status/{link}` перенёс; затем весь цикл
`start → done --review → done → block → start` подтверждён отдельным запросом после
каждого перехода.
**Откат:** н/п.

## 2026-09-07 — системные колонки материализуются лениво
**Что:** `init` определяет системные колонки запросом по детерминированному id
(`GET /kanban-status/KS-<projectId>-TODO`), а не по наличию в списке; `doctor` ругается на
колонки-тёзки; порядок своих колонок считается от фактических соседей.
**Почему:** в свежесозданном проекте `GET /kanban-status?projectId=…` вернул пустой список,
скилл создал свои пять колонок — а потом системные проявились, и на доске стало 7 колонок
с двумя «В работе» и двумя «Готово». Плюс сервер сам пересчитывает `kanbanOrder`
(системная «В работе» уехала с 50000 на 89583), поэтому фиксированные числа порядка
ломают раскладку.
**Как проверено:** дубли удалены, конфиг перепривязан на системные колонки, повторный
`init` печатает «ИСПОЛЬЗОВАТЬ системную колонку» вместо создания; порядок на доске —
Новые → В работе → На проверке → Готово → Заблокировано.
**Откат:** колонки пересоздаются `init --apply`.
