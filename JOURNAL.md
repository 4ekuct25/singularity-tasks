# Журнал решений

## 2026-09-07 — заметка это массив операций, а не объект `{"ops":…}`
**Что:** `note_append`/`note_to_text` переписаны: пишется голый массив
`[{"insert":"текст\n"}]`; чтение понимает три формы (массив, объект-обёртку, простой
текст). Переписаны заметки всех 12 заведённых задач.
**Почему:** спека говорит только «Task note in delta format» и про форму умалчивает.
Я выбрал каноничный для Quill объект `{"ops":[...]}` — API его принял, вернул обратно
байт в байт, и `note_to_text` читал его корректно. То есть **все мои проверки шли через
API и сходились**, а приложение эту форму разобрать не может и рисует в карточке сырой
JSON. Дефект увидел пользователь глазами, не проверки: контур «записал → прочитал через
тот же слой» в принципе не способен показать такую ошибку.
**Как проверено:** по локальной базе приложения (`nedb-backup/AppDatabase_*.json`):
из 704 заметок 698 — массивы операций, объектов-обёрток ноль. Заодно выяснилось, что в
базе `note` у задачи — это ссылка `N-T-<id>` на отдельную коллекцию `notes`, а текст
лежит в её поле `content`. После правки все 12 задач отдают `note`, начинающийся с `[`,
задач с прежним форматом — 0.
**Откат:** формат заметок переписывается тем же циклом в обратную сторону; данные не
терялись — текст извлекался из старой формы и перекладывался в новую.

## 2026-09-07 — раскатка в четыре агентских окружения
**Что:** `tools/install.sh` переписан на несколько целей — Claude Code, Codex, OpenCode,
Antigravity; добавлены `--list` и `--target`. Отсутствующие на машине инструменты
пропускаются, бэкап делается на каждую цель отдельно в `~/.singularity-tasks-backup/`.
**Почему:** формат SKILL.md общий для всех четырёх, различаются только каталоги; ручное
копирование в четыре места гарантированно разъезжается.
**Как проверено:** `--list` до раскатки показал 1 установленную цель из 4, после — все 4
«совпадает»; `doctor` запущен из каждой из четырёх копий, все четыре видят токен и
привязку; повторный запуск сообщает «всё уже актуально» (идемпотентность).
**Откат:** `rm -rf <путь-цели> && mv ~/.singularity-tasks-backup/<цель> <путь-цели>`

## 2026-09-07 — у семейства Gemini два разных каталога скиллов
**Что:** цель `antigravity` указывает на `~/.gemini/config/skills/`, а не на
`~/.gemini/skills/`.
**Почему:** `~/.gemini/skills/` читает **Gemini CLI**, Antigravity туда не смотрит; его
глобальные скиллы лежат в `~/.gemini/config/skills/`. Косвенное подтверждение с машины:
`~/.gemini/config/` содержит `plugins/` и `mcp_config.json`, то есть это конфигурационный
корень Antigravity, а `~/.gemini/skills/` пуст, хотя личные скиллы разложены во все
остальные инструменты. Наблюдение про среду, кода не касается.
**Как проверено:** раскатка в `~/.gemini/config/skills/singularity-tasks`, `doctor` из
этой копии проходит. ⚠️ Что Antigravity действительно **подхватывает** скилл, не
проверено — нужен запуск IDE и вопрос «какие скиллы доступны».
**Откат:** н/п.

## 2026-09-07 — привязка репозитория вынесена из `.claude/`
**Что:** конфиг ищется в `.agents/singularity.json` → `.claude/singularity.json` → в корне;
новые репозитории получают `.agents/`, уже привязанные переписываются на месте.
**Почему:** скилл работает в четырёх инструментах, а привязка лежала в каталоге одного из
них — для Codex, OpenCode и Antigravity это чужой каталог.
**Как проверено:** существующая привязка в `.claude/` читается и `init` пишет туда же (не
плодит второй файл); во временном каталоге `init` предлагает `.agents/`; при наличии обоих
файлов выигрывает `.agents/`.
**Откат:** вернуть однопутевой `find_config`, файлы не трогаются.

## 2026-09-07 — рекурсивная сверка ловила мусор компиляции
**Что:** в `tools/install.sh` сравнение и копирование исключают `__pycache__` и `*.pyc`,
добавлен `.gitignore`.
**Почему:** `python3 -m py_compile` в самом репозитории создал `scripts/__pycache__`,
и рекурсивный `diff` объявил расхождением то, что частью скилла не является. Установка
падала на строчке «после установки всё ещё расходится» — то есть проверка была честной,
но сравнивала не то.
**Как проверено:** после фикса все четыре цели дают «совпадает», повторная раскатка —
«всё уже актуально».
**Откат:** н/п.

## 2026-09-07 — `set -e` + `pipefail` съедали установку
**Что:** в `tools/install.sh` диагностический вывод `diff` обёрнут в `|| true`.
**Почему:** `diff` возвращает 1 при различиях; при `set -euo pipefail` пайплайн
`diff | sed | head` валил скрипт ровно в тот момент, когда расхождение найдено — то есть
установка не выполнялась именно тогда, когда была нужна. Хуже того, `--check` при этом
возвращал 1 «правильно», но по аварии, а не по логике: проверка давала верный ответ по
неверной причине и потому ничего не доказывала.
**Как проверено:** после фикса `--check` при расхождении печатает подсказку и возвращает 1,
`install.sh` доходит до копирования, повторный `--check` даёт совпадение.
**Откат:** н/п.

## 2026-09-07 — API отвечает 200, ничего не сделав
**Что:** перенос задач по колонкам переведён с `POST /task/{id}/change-column` на
`PATCH /kanban-task-status/{link}` с обязательным перечитыванием состояния.
**Почему:** `change-column` на **системных** колонках проекта (`KS-<projectId>-TODO` и
компания) отвечает `200` и возвращает задачу, но связку не меняет. На пользовательских
колонках он работает — поэтому первый прогон, шедший по своим колонкам, ничего не выявил.
Из-за доверия к коду ответа одна задача осиротела при удалении колонки под ней.
**Как проверено:** перебором способов на живой задаче — `PATCH /task {kanbanStatusId}` не
сработал, `PATCH /kanban-task-status/{link}` перенёс; затем весь цикл
`start → done --review → done → block → start` подтверждён отдельным запросом после
каждого перехода.
**Откат:** н/п.

## 2026-09-07 — системные колонки материализуются лениво
**Что:** `init` определяет системные колонки запросом по детерминированному id
(`GET /kanban-status/KS-<projectId>-TODO`), а не по наличию в списке; `doctor` ругается на
колонки-тёзки; порядок своих колонок считается от фактических соседей.
**Почему:** в свежесозданном проекте `GET /kanban-status?projectId=…` вернул пустой список,
скилл создал свои пять колонок — а потом системные проявились, и на доске стало 7 колонок
с двумя «В работе» и двумя «Готово». Плюс сервер сам пересчитывает `kanbanOrder`
(системная «В работе» уехала с 50000 на 89583), поэтому фиксированные числа порядка
ломают раскладку.
**Как проверено:** дубли удалены, конфиг перепривязан на системные колонки, повторный
`init` печатает «ИСПОЛЬЗОВАТЬ системную колонку» вместо создания; порядок на доске —
Новые → В работе → На проверке → Готово → Заблокировано.
**Откат:** колонки пересоздаются `init --apply`.
