# SingularityApp API — справочник

Спека: `https://api.singularity-app.com/v2/api-json` (OpenAPI 3.0, NestJS/Swagger).
Живой Swagger UI: `https://api.singularity-app.com/v2/api`.

## Авторизация

`Authorization: Bearer <token>`, схема `rest-token`. Токен создаётся на
me.singularity-app.com → API. Отредактировать существующий токен нельзя — только
удалить и создать новый.

## Префиксы идентификаторов

| Префикс | Сущность |
|---|---|
| `P-` | проект |
| `Q-` | группа задач (секция) |
| `T-` | задача |
| `A-` | тег |
| `KS-` | канбан-колонка |
| `KTS-` | связка задача↔колонка |

## Эндпоинты

CRUD у всех сущностей одинаковый: `GET/POST /v2/<x>`, `GET/PATCH/DELETE /v2/<x>/{id}`.
Сущности: `project`, `task-group`, `task`, `kanban-status`, `kanban-task-status`,
`habit`, `habit-progress`, `checklist-item`, `tag`, `time-stat`.

Действия сверх CRUD:

- `POST /v2/task/{id}/complete` · `/uncomplete` · `/cancel` · `/complete-today`
- `POST /v2/task/{id}/archive` · `/unarchive`
- `POST /v2/task/{id}/move` — `{projectId, groupId?, parent?}`
- `POST /v2/task/{id}/change-column` — `{statusId}`
- `POST /v2/project/{id}/archive` · `/unarchive`
- `POST /v2/checklist-item/{id}/check` · `/uncheck`
- `POST /v2/batch` — пачка `{method, path, body, uuid?, tempId?}`, методы POST/PATCH/DELETE

## Формы ответов

Списки завёрнуты в именованный ключ, не голый массив:
`{projects: []}`, `{tasks: []}`, `{kanbanStatuses: []}`, `{kanbanTaskStatuses: []}`,
`{tags: []}`, `{checklistItems: []}`. Блок `pagination {total, count, offset}`
появляется только при `paginationData=true`.

## Подводные камни

- ⚠ **`note` — Quill-delta в виде ГОЛОГО МАССИВА операций**: строка с JSON
  `[{"insert":"текст\n"}]`. Обёртка `{"ops":[...]}` — **неверно**: API её принимает и
  отдаёт обратно, а приложение разобрать не может и рисует в карточке сырой JSON вместо
  текста. Спека говорит только «note in delta format» и про форму умалчивает.
  Проверено по локальной базе приложения: из 704 заметок 698 — массивы, остальные
  legacy-текст. `sing.py` читает все три формы (массив, объект-обёртку, простой текст),
  но пишет только массив.
- **Операции могут нести оформление:** `{"insert": "Ссылка", "attributes": {"link": "..."}}`.
  Дописывать отчёт надо новой операцией в конец, не пересобирая заметку из текста —
  иначе слетят ссылки и форматирование, сделанные человеком.
- **Пагинация задач ломается** без `includeAllRecurrenceInstances=true`: при значении по
  умолчанию сервер префильтрует выборку уже после выборки строк, `count` выходит меньше
  `maxCount`, а offset-пагинация даёт пропуски. Прямая цитата из спеки:
  «For reliable offset-pagination over `task` pass `includeAllRecurrenceInstances=true`».
- ⚠ **`offset` шагает по ЗАПРОШЕННОМУ окну, а не по числу отданных строк.** Из-за
  post-фильтра (выше) `count` бывает меньше `maxCount`; если двигать offset на
  `len(batch)`, окна идут внахлёст — строки повторяются, а хвост не доезжает. Замер на
  заглушке: из 450 строк, где сервер отдаёт 300, шаг по `len(batch)` вернул 450 строк с
  дублями и 300 уникальных, шаг по окну — ровно 300 без дублей.
- **`pagination.total` — не условие остановки.** Он считается до post-фильтра, поэтому
  `offset >= total` обрывает обход раньше времени. Надёжный выход — пустая страница;
  `total` годится только чтобы ЗАМЕТИТЬ недобор и сказать о нём вслух.
- **`maxCount` больше 200 сервер принимает** (проверено до 1000, отдаёт сколько есть), но
  `sing.py` держит окно в 200: большие окна на запись (`/batch`) упираются в
  `504 Gateway Time-out` от nginx.
- **Троттлинг есть, хотя в документации не заявлен:** обход проекта в 1150 задач стабильно
  ловит `429 ThrottlerException`. `request()` повторяет 429/5xx с экспоненциальной паузой.
- **`POST /v2/batch` — объект `{"operations": [...]}`**, не голый массив; не больше
  **100** операций; `path` обязан начинаться с `/v2/`, `tempId` — с `tmp:`. На пачках по
  25–50 операций создание задач регулярно отваливается по `504` (часть операций при этом
  всё же применяется — счёт «сколько создано» по коду ответа недостоверен). Пачки по 10
  идут ровно, ~6 объектов/с.
- **`DELETE /v2/project/{id}` уносит задачи асинхронно:** ответ приходит сразу, а задачи
  вычищаются фоном — наблюдалось около 1 задачи/с, проект исчезает из `GET /v2/project`
  только после них. Проверять уборку надо перечитыванием с паузой, а не по коду ответа.
- **Колонка задачи не лежит в самой задаче.** Определяется через
  `GET /v2/kanban-task-status?taskId=T-...`. Фильтра по колонке у `/v2/task` нет.
  Связка одна на задачу, её id детерминирован: `KTS-<taskId>`.
- ⚠ **`POST /v2/task/{id}/change-column` молча не работает на системных колонках:**
  отвечает `200` и возвращает задачу, но связку не меняет. На пользовательских колонках
  работает. `sing.py` им не пользуется вообще — правит связку через
  `PATCH /v2/kanban-task-status/{KTS-...}` и **перечитывает состояние**, чтобы не принять
  успешный код за факт переноса.
- **`PATCH /v2/kanban-task-status` не принимает поле `removed`** (`400 property removed
  should not exist`). Воскресить помеченную удалённой связку нельзя — нужен новый
  `POST /v2/kanban-task-status {taskId, statusId}`.
- **Удаление колонки осиротит задачи:** связка получает `removed=true`, задача пропадает
  с доски, но остаётся в проекте. Перед `DELETE /v2/kanban-status/{id}` переносить задачи.
- **Перенос из done-колонки снимает отметку выполнения** (`checked` 1 → 0). Обратное тоже:
  колонка и `checked` связаны серверной логикой, а не только вашими вызовами.
- ⚠ **Системные колонки проекта** имеют детерминированные id
  `KS-<projectId>-TODO` / `-IN-PROGRESS` / `-DONE` (названия «Новые», «В работе», «Готово»).
  Сервер материализует их **лениво**: в только что созданном проекте
  `GET /v2/kanban-status?projectId=…` может вернуть пустой список, а колонки появятся
  позже — и тогда рядом с ними встанут дубли, если вы создали свои. Проверять
  существование надо запросом по id (`GET /v2/kanban-status/KS-<projectId>-TODO`), а не
  наличием в списке.
- **`kanbanOrder` пересчитывается сервером** (системные шли 0/50000/100000, после
  удаления колонок «В работе» оказалась на 89583). Позицию своих колонок считать от
  фактических соседей, не по фиксированным числам.
- **Числа, а не имена:** `priority` 0=высокий/1=обычный/2=низкий; `checked`
  0=пусто/1=выполнено/2=отменено; `state` 0=закреплена/1=нет.
- **`journalDate` = архивация.** Заполнять только если реально нужно отправить в архив.
- **Нет вебхуков**, потоков событий и подписок — только polling. Для инкремента есть
  `modifiedSince` (полный ISO с временем).
- **Группа задач и колонка ортогональны:** задача одновременно лежит в секции (`group`)
  и стоит в канбан-колонке, перенос по доске поле `group` не трогает. У каждого проекта
  есть служебная группа с `fake=true` и пустым названием — это не секция, её надо
  отфильтровывать.
- **Заметки (`isNote=true`) — это задачи**, лежащие в проекте, но не на канбане:
  `kanban-task-status` у них нет. Их надо явно исключать из выборок задач, иначе агент
  попробует «выполнить» заметку.
- **Общие/расшаренные проекты** через API не отдаются, только личные.
- **Повторяющиеся задачи** через API не создаются.
- **`tags` у задачи — массив id тегов**, а не объектов. PATCH перезаписывает список
  целиком, поэтому добавлять тег можно только «прочитал → дописал → записал», иначе
  затрёте чужие. Теги общие на аккаунт, привязки к проекту у них нет.
- Rate limit в документации не заявлен — не долбить в цикле без пауз.

## MCP-сервер (альтернатива CLI)

- Endpoint: `https://mcp.singularity-app.com/mcp`, требует тариф Pro/Elite.
- Авторизация: Bearer в заголовке (`bearer_methods_supported: ["header"]`),
  authorization server — `https://me.singularity-app.com`.
- Скоупы: `tasks:read|write|check`, `projects:*`, `kanban:*`, `checklists:*`,
  `habits:*`, `tags:*`, `time_stat:*`, `mcp:*`.
- Набор инструментов сужается query-параметром:
  `?toolsets=tasks,projects,kanban,tags,habits,time,meta,system`.
- Подключение: `claude mcp add --transport http singularity https://mcp.singularity-app.com/mcp`
  (авторизация — интерактивно через `/mcp`). Точный список tool'ов сервер отдаёт
  на `tools/list` после авторизации; публичной документации по нему нет.
