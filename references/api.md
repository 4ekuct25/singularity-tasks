# SingularityApp API — справочник

Спека: `https://api.singularity-app.com/v2/api-json` (OpenAPI 3.0, NestJS/Swagger).
Живой Swagger UI: `https://api.singularity-app.com/v2/api`.

## Авторизация

`Authorization: Bearer <token>`, схема `rest-token`. Токен создаётся на
me.singularity-app.com → API. Отредактировать существующий токен нельзя — только
удалить и создать новый.

## Префиксы идентификаторов

| Префикс | Сущность |
|---|---|
| `P-` | проект |
| `Q-` | группа задач (секция) |
| `T-` | задача |
| `A-` | тег |
| `CH-` | пункт чек-листа |
| `KS-` | канбан-колонка |
| `KTS-` | связка задача↔колонка |

## Эндпоинты

CRUD у всех сущностей одинаковый: `GET/POST /v2/<x>`, `GET/PATCH/DELETE /v2/<x>/{id}`.
Сущности: `project`, `task-group`, `task`, `kanban-status`, `kanban-task-status`,
`habit`, `habit-progress`, `checklist-item`, `tag`, `time-stat`.

Действия сверх CRUD:

- `POST /v2/task/{id}/complete` · `/uncomplete` · `/cancel` · `/complete-today`
- `POST /v2/task/{id}/archive` · `/unarchive`
- `POST /v2/task/{id}/move` — `{projectId, groupId?, parent?}`
- `POST /v2/task/{id}/change-column` — `{statusId}`
- `POST /v2/project/{id}/archive` · `/unarchive`
- `POST /v2/checklist-item/{id}/check` · `/uncheck`
- `POST /v2/batch` — пачка `{method, path, body, uuid?, tempId?}`, методы POST/PATCH/DELETE

## Формы ответов

Списки завёрнуты в именованный ключ, не голый массив:
`{projects: []}`, `{tasks: []}`, `{kanbanStatuses: []}`, `{kanbanTaskStatuses: []}`,
`{tags: []}`, `{checklistItems: []}`. Блок `pagination {total, count, offset}`
появляется только при `paginationData=true`.

## Подводные камни

- ⚠ **`note` — Quill-delta в виде ГОЛОГО МАССИВА операций**: строка с JSON
  `[{"insert":"текст\n"}]`. Обёртка `{"ops":[...]}` — **неверно**: API её принимает и
  отдаёт обратно, а приложение разобрать не может и рисует в карточке сырой JSON вместо
  текста. Спека говорит только «note in delta format» и про форму умалчивает.
  Проверено по локальной базе приложения (снапшот 2026-09-11, 726 заметок):
  **голый массив — 720 (99.2 %), простой текст без JSON — 4, пустая строка — 2,
  объект-обёртка — 0.** `sing.py` читает все три формы (массив, объект-обёртку,
  простой текст), но пишет только массив.
- **Операции могут нести оформление:** `{"insert": "Ссылка", "attributes": {"link": "..."}}`.
  Дописывать отчёт надо новой операцией в конец, не пересобирая заметку из текста —
  иначе слетят ссылки и форматирование, сделанные человеком.
- **Словарь `attributes`, который приложение реально рисует** (частоты из той же базы,
  1028 операций с оформлением). Ориентироваться надо на него, а не на документацию
  Quill: часть ключей у приложения своя, а часть общих Quill-ключей не встречается:

  | attribute | значения | сколько |
  |---|---|---|
  | `list` | `bullet`, `ordered`, `checked`, `unchecked` | 382 |
  | `link` | URL строкой | 373 |
  | `sx-table-cell-line` | объект `{table,row,cell,ancestor,@containerId,@containerType}` | 102 |
  | `bold` | `true` | 73 |
  | `align` | `center` | 58 |
  | `indent` | `1`..`4` | 29 |
  | `header` | `2`, `3` | 18 |
  | `sx-table-column` | объект, опционально с `width` | 10 |
  | `italic` | `true` | 9 |
  | `singularityBackgroundAttribute` | `red`, `green` — **имя цвета, не hex** | 4 |
  | `singularityColorAttribute` | `red` | 1 |

  Чек-лист внутри заметки — это `list: "checked"` / `"unchecked"`, отдельной сущности нет.
  Встраиваемые объекты приходят как `insert`-объект, а не строка: `image` (62), `divider` (5).
- ⚠ **В самой задаче заметки нет — API её подставляет.** В локальной базе
  `tasks.note` — это **идентификатор** записи заметки, детерминированный
  `N-<taskId>` (665 из 665 непустых значений — ссылка на `notes.id`, 100 %), а тело
  лежит отдельной коллекцией `notes` в поле `content`. `notes.id == "N-" + containerId`
  для всех 726 записей; `containerId` — задача (709) или проект (17), то есть заметки
  проекта и заметки задачи — одна и та же сущность с разным владельцем.
  Через API этого не видно: `GET /v2/task/{id}` отдаёт в `note` уже саму дельту
  строкой. Практический вывод: одна заметка на владельца, «вторую» создать нельзя,
  а правка `note` перезаписывает общую запись целиком.
- **Пустой `note` у задачи не значит «заметки нет».** Записей `notes` с владельцем-задачей
  709, владелец найден в снапшоте у 708, а поле `note` заполнено только у 665: у 43 задач
  запись заметки существует и **непустая**, а указателя в задаче нет. Пустых `content`
  среди них ноль. То есть связь держится соглашением `N-<taskId>`, а поле `note` —
  кэш-указатель, который может отсутствовать. Отдаёт ли API текст для таких задач,
  проверить не удалось: все 43 лежат вне «ИИ проекты», а запрашивать чужие задачи скилл
  не имеет права.
- **Пагинация задач ломается** без `includeAllRecurrenceInstances=true`: при значении по
  умолчанию сервер префильтрует выборку уже после выборки строк, `count` выходит меньше
  `maxCount`, а offset-пагинация даёт пропуски. Прямая цитата из спеки:
  «For reliable offset-pagination over `task` pass `includeAllRecurrenceInstances=true`».
- ⚠ **`offset` шагает по ЗАПРОШЕННОМУ окну, а не по числу отданных строк.** Из-за
  post-фильтра (выше) `count` бывает меньше `maxCount`; если двигать offset на
  `len(batch)`, окна идут внахлёст — строки повторяются, а хвост не доезжает. Замер на
  заглушке: из 450 строк, где сервер отдаёт 300, шаг по `len(batch)` вернул 450 строк с
  дублями и 300 уникальных, шаг по окну — ровно 300 без дублей.
- **`pagination.total` — не условие остановки.** Он считается до post-фильтра, поэтому
  `offset >= total` обрывает обход раньше времени. Надёжный выход — пустая страница;
  `total` годится только чтобы ЗАМЕТИТЬ недобор и сказать о нём вслух.
- **`maxCount` больше 200 сервер принимает** (проверено до 1000, отдаёт сколько есть), но
  `sing.py` держит окно в 200: большие окна на запись (`/batch`) упираются в
  `504 Gateway Time-out` от nginx.
- **Троттлинг есть, хотя в документации не заявлен:** обход проекта в 1150 задач стабильно
  ловит `429 ThrottlerException`. `request()` повторяет 429/5xx с экспоненциальной паузой.
- **`POST /v2/batch` — объект `{"operations": [...]}`**, не голый массив; не больше
  **100** операций; `path` обязан начинаться с `/v2/`, `tempId` — с `tmp:`. На пачках по
  25–50 операций создание задач регулярно отваливается по `504` (часть операций при этом
  всё же применяется — счёт «сколько создано» по коду ответа недостоверен). Пачки по 10
  идут ровно, ~6 объектов/с.
- **`DELETE /v2/project/{id}` уносит задачи асинхронно:** ответ приходит сразу, а задачи
  вычищаются фоном — наблюдалось около 1 задачи/с, проект исчезает из `GET /v2/project`
  только после них. Проверять уборку надо перечитыванием с паузой, а не по коду ответа.
- **Колонка задачи не лежит в самой задаче.** Определяется через
  `GET /v2/kanban-task-status?taskId=T-...`. Фильтра по колонке у `/v2/task` нет.
- ⚠ **Id связки НЕ всегда `KTS-<taskId>`, и колонка не всегда из проекта задачи.**
  Кроме проектных досок есть системная доска «Сегодня» — псевдопроект `P-TODAY` со
  своими колонками (`KS-P-TODAY-TODO` / `-IN-PROGRESS` / `-DONE` плюс пользовательские).
  Связка с ней имеет id `KTS-<taskId>-TODAY`. В локальной базе таких **23 из 46 связок
  (50 %)**, и все 23 задачи принадлежат обычным проектам. Следствия:
  - вычислять id связки как `KTS-<taskId>` нельзя — попадёте не в ту запись или в никуда;
  - первая попавшаяся связка задачи может указывать на колонку доски «Сегодня»;
    для доски проекта такая задача выглядит «вне колонок», хотя связка есть;
  - PATCH такой связки уберёт задачу с «Сегодня» вместо переноса по доске проекта.

  Связку выбирать по принадлежности `statusId` колонкам нужного проекта, а не по
  порядку в ответе. В `sing.py` это делают `board_links()` / `project_status_ids()`.
- **`POST /v2/kanban-task-status` не принимает поле `id`** (`400 property id should not
  exist`) и выводит id из `taskId`: повторный POST для той же задачи не заводит вторую
  связку, а **апсертит `KTS-<taskId>`** — переставляет её на новую колонку. Через
  `/v2/batch` то же самое. Следствие для проверок: состояние «две связки сразу» через
  REST не создать, `KTS-<taskId>-TODAY` заводит только само приложение — этот случай
  проверяется заглушкой (`tools/check-today-link.py --stub`), а не живьём. Задача,
  у которой единственная связка указывает на колонку `P-TODAY`, воспроизводится одним POST.
- **Поле `start` (плановая дата) связку с «Сегодня» не создаёт:** PATCH `start` = сегодня
  на задачу без связки `-TODAY` ничего в `kanban-task-status` не добавил.
- ⚠ **`POST /v2/task/{id}/change-column` молча не работает на системных колонках:**
  отвечает `200` и возвращает задачу, но связку не меняет. На пользовательских колонках
  работает. `sing.py` им не пользуется вообще — правит связку через
  `PATCH /v2/kanban-task-status/{id связки, взятый из ответа}` и **перечитывает
  состояние**, чтобы не принять успешный код за факт переноса.
- **`PATCH /v2/kanban-task-status` не принимает поле `removed`** (`400 property removed
  should not exist`). Воскресить помеченную удалённой связку нельзя — нужен новый
  `POST /v2/kanban-task-status {taskId, statusId}`.
- **Удаление колонки осиротит задачи:** связка получает `removed=true`, задача пропадает
  с доски, но остаётся в проекте. Перед `DELETE /v2/kanban-status/{id}` переносить задачи.
- **Перенос из done-колонки снимает отметку выполнения** (`checked` 1 → 0). Обратное тоже:
  колонка и `checked` связаны серверной логикой, а не только вашими вызовами.
- ⚠ **Системные колонки проекта** имеют детерминированные id
  `KS-<projectId>-TODO` / `-IN-PROGRESS` / `-DONE` (названия «Новые», «В работе», «Готово»).
  Проверять существование надо запросом по id (`GET /v2/kanban-status/KS-<projectId>-TODO`),
  а не наличием в списке. Кто и когда их создаёт — ниже, в пункте про клиента; прежняя
  формулировка «сервер материализует лениво» **неверна** и опровергнута замером.
- **`kanbanOrder` пересчитывается сервером** (системные шли 0/50000/100000, после
  удаления колонок «В работе» оказалась на 89583). Позицию своих колонок считать от
  фактических соседей, не по фиксированным числам.
- **Числа, а не имена:** `priority` 0=высокий/1=обычный/2=низкий; `checked`
  0=пусто/1=выполнено/2=отменено; `state` 0=закреплена/1=нет.
  По базе (2217 задач): `priority` — только 0/1/2 (1×2195, 0×19, 2×3), `state` —
  только 0/1, `checked` — **только 0 и 1** (1×1473, 0×744), значение 2 на живых
  данных не встречается ни разу. Рядом живёт отдельное поле `complete` со
  значениями 0…4 — оно не синоним `checked`, скилл его не трогает.
- **У пункта чек-листа отметка — булево `done`, а не числовой `checked` задачи.** Это
  разные поля с разной кодировкой, перепутать легко (замер: `GET /v2/checklist-item/CH-…`
  после `POST /v2/checklist-item/{id}/check` отдаёт `"done": true`, список
  `GET /v2/checklist-item?parent=T-…` — то же самое значение). Порядок пунктов задаёт
  `parentOrder`; `POST /checklist-item` без него пункты не упорядочит, поэтому `sing.py`
  считает его от максимума существующих — новые уходят в конец и не сдвигают нумерацию
  уже показанных пунктов.
- ⚠ **`journalDate` = «унесено в дневник» (архив), а НЕ удаление.** Проверено на живом API:
  `POST /task/{id}/archive` ставит `journalDate` и заодно `checked=1`, при этом
  `removed=false`, `deleteDate=null`, а связка с колонкой (`kanban-task-status`) остаётся
  живой (`removed=false`) — задача по-прежнему стоит в своей колонке. `unarchive`
  снимает `journalDate` и возвращает `checked` в 0. Удаление — другое: `DELETE /v2/task/{id}`
  ставит `removed=true` и `journalDate` не трогает, а корзина приложения ставит
  `deleteDate` при `removed=false`.
- ⚠ **Выборку режет сервер, а не только ваш фильтр.** `GET /v2/task` по умолчанию не
  отдаёт ни архив, ни удалённое, и флаги на них **разные**: `includeArchived=true`
  возвращает задачи с `journalDate`, `includeRemoved=true` — с `removed`/`deleteDate`.
  Замер на черновом проекте: 5 задач → после complete/archive/delete в выдаче осталось 2,
  с `includeArchived=true` — 4, с обоими флагами — 5. Поэтому «поправить клиентский
  фильтр» недостаточно: без флага архивных задач в ответе просто нет. Есть и фильтр
  `journalDate.isSet=true|false`, чтобы забрать только дневник или только активное.
- **Отсюда правило скилла:** брать в работу можно только задачи без `journalDate`
  (`live_tasks()`), а показывать историю сделанного — вместе с ними (`board_tasks()`,
  из неё читает `board`). Закрытая задача в дневнике жива, и «Готово» обязано её видеть.
- ⚠ **Даты — полный ISO с `Z`, но дробная часть НЕ фиксирована.** `deadline`, `start`,
  `journalDate`, `deleteDate`, `createdDate` в базе встречаются в трёх видах сразу:
  6 знаков после запятой, 3 знака и вовсе без них — `createdDate`: 1721 / 391 / 105 по
  этим трём формам, `start`: 2000 / 16, `journalDate`: 883 / 557. Парсер, прибитый к
  `%Y-%m-%dT%H:%M:%S.%fZ`, упадёт на 391 задаче из 2217. Исключение — `seenToday`:
  он **date-only** `YYYY-MM-DD` (1497 из 1497), хотя лежит рядом с остальными.
  Отсутствующее значение в базе — **нет ключа**, а API на том же месте отдаёт `null`;
  «пусто» и «не задано» по этому не различить.
  `deadline` на живых данных практически не используется: заполнен у 3 задач из 2217.
- **`_removed` (int 0/1) в базе против `removed` (bool) в API** — это одно и то же поле
  под разными именами и типами. Фильтровать удалённое надо по тому имени, которое
  отдаёт ваш источник, а не по привычному.
- **Что есть в базе, но не отдаётся через API:** `recurrence` (объект из 11–13 ключей,
  31 задача), `modificated` (словарь «поле → timestamp», у каждой задачи — на нём
  построено слияние правок в приложении), `notifies` в базе — список int (668 задач).
  Повторяющиеся задачи материализуются экземплярами с id `T-<uuid>-YYYYMMDD`
  (348 из 665 непустых `note` принадлежат именно таким экземплярам) — это не опечатка
  и не другой префикс, а обычная задача-экземпляр.
- **Нет вебхуков**, потоков событий и подписок — только polling. Для инкремента есть
  `modifiedSince` (полный ISO с временем).
- **Группа задач и колонка ортогональны:** задача одновременно лежит в секции (`group`)
  и стоит в канбан-колонке, перенос по доске поле `group` не трогает. У каждого проекта
  есть служебная группа с `fake=true` и пустым названием — это не секция, её надо
  отфильтровывать. По базе: 56 fake-групп из 79, у всех 56 пустое название, и наоборот —
  пустого названия у настоящей секции нет ни одного. Отфильтровывать можно по любому из
  двух признаков, а вот **вычислять id служебной группы нельзя**: `Q-<projectId>`
  совпадает лишь у 9 из 56, остальные — обычные `Q-<uuid>`.
- **Заметки (`isNote=true`) — это задачи**, лежащие в проекте, но не на канбане:
  `kanban-task-status` у них нет. Их надо явно исключать из выборок задач, иначе агент
  попробует «выполнить» заметку.
- **Общие/расшаренные проекты** через API не отдаются, только личные.
- **Повторяющиеся задачи** через API не создаются.
- **`tags` у задачи — массив id тегов**, а не объектов. PATCH перезаписывает список
  целиком, поэтому добавлять тег можно только «прочитал → дописал → записал», иначе
  затрёте чужие. Теги общие на аккаунт, привязки к проекту у них нет. Подтверждено по
  базе: 2217 задач, `tags` есть у всех, форма — либо пустой список (1454), либо
  список строк `A-<uuid>` (763); объектов внутри нет ни одного.
- ⚠ **Запись видна не сразу: сервер отвечает `200` РАНЬШЕ, чем применит её.** Тот же
  механизм, что у `DELETE /tag` («Sync error … number in queue N»): PATCH кладётся в
  очередь синхронизации, и на загруженной очереди немедленно следующий `GET /task/{id}`
  отдаёт ещё прежний список тегов. Замер (T-fc3a3096): на очереди `number in queue`
  7→15 перехват падал 2 прогона из 2, на спокойной проходил с первого чтения.
  Отсюда два правила:
  · **подтверждать запись не первым чтением, а перечитыванием с паузой** — одно чтение
    в принципе не отличает «ещё не применил» от «не применил», оно одинаково видит
    старое (`TAG_SETTLE_TRIES` / `TAG_SETTLE_PAUSE` в `set_task_tags`, как
    `SETTLE_TRIES` в `tools/zz-project.py`);
  · **не разбивать одну смену состояния на два PATCH.** `tags` перезаписывается
    целиком, поэтому «снять чужой тег» и «повесить свой» — это один запрос, а не два.
    Два дают окно, в котором задача уже не чужая, но ещё не моя: под лагом второй
    PATCH не подтверждался, и задача оставалась вообще без `agent:*` — выглядела
    свободной, хотя её только что перехватывали. Повтором это не лечится, только
    слиянием в одну запись.
  Обратная сторона: **повторять сам PATCH в подтверждении нельзя.** Запись не
  теряется — она отстаёт; а повтор переписал бы встречный захват и сломал правило
  «победитель ровно один» в `claim_task`.
- **`title` — простой текст, без разметки.** 2217 из 2217 — строка; дельт, HTML и
  JSON там не бывает (у 42 заголовков внутри есть угловые скобки, у 5 текст
  начинается с `[` или `{` — это именно текст). Заголовок не парсить как структуру.
- ⚠ **`tags` у задачи могут пропасть пачкой, и не по вине скилла.** Наблюдение: в одном
  проекте 16 из 23 закрытых карточек оказались с пустым `tags`, при том что `mark_agent()`
  ставит метку на каждой команде. Потеря легла **окном** по `modificatedDate` (все
  пострадавшие правились в один 18-минутный промежуток), а девять из них несут одну и ту
  же метку времени — то есть писал кто-то пачкой, а `sing.py` пишет по одной задаче.
  Контроль: в соседнем проекте того же аккаунта теги уцелели все, значит процесс не
  общеаккаунтный. Восстановленный тег держится — потеря разовая. Виновник не установлен;
  локальная база приложения тут не помощник, она отдаёт только суточные снапшоты.
  **Практический вывод:** не считать `agent:*` надёжным хранилищем факта «кто сделал».
  Дублирующий след есть в самой заметке — ярлык `РЕЗУЛЬТАТ (agent:X)`, по нему теги
  восстанавливаются механически.
- ⚠ **Тег удалить нельзя — ни `DELETE`, ни `removed`.** `DELETE /tag/{id}` отвечает
  `500 Sync error: Please try again later /…/ number in queue N`, и это не всплеск
  нагрузки: воспроизводится и через минуту (замер: очередь выросла с 7 до 14, тег на
  месте). `PATCH {"removed": true}` тоже не проходит, `removed` остаётся `false`.
  Следствие для проверок: **имена пробных агентов должны быть фиксированными**
  (`ensure_tag` переиспользует существующий тег), иначе каждый прогон добавляет в
  общий на аккаунт список новую строку, и убрать её потом нечем. Так уже накопились
  `agent:zz-agent-0…3`, `agent:zz-first`, `agent:zz-second` от прогонов
  `tools/check-claim-race.py -n`, где имя зависит от номера агента.
- Rate limit в документации не заявлен, но он есть: под четырьмя параллельными агентами
  живой API отдавал `429 ThrottlerException`. `request()` на `429` ждёт столько, сколько
  просит `Retry-After` (он бывает и числом секунд, и HTTP-датой), без заголовка — своя
  нарастающая пауза; потолки `RETRY_AFTER_CAP` / `RETRY_WAIT_BUDGET`, чтобы команда не
  висела на `Retry-After: 3600`.
- **Повторять можно не всё.** `429` сервер отдаёт, ОТКАЗАВШИСЬ обслужить запрос — он не
  выполнен, поэтому повтор безопасен для любого метода, включая `POST`. `5xx` означает
  «принял и сломался»: запрос мог примениться, и повторяется только `GET`, иначе появится
  второй объект. Остальные `4xx` не повторяются вовсе.
- ⚠ **`URLError` покрывает не весь сетевой сбой.** urllib заворачивает в неё только
  установку соединения и отправку запроса (`OSError` из `h.request()`). Всё, что случилось
  ПОСЛЕ, прилетает как есть: сервер принял соединение и молчит — голый `TimeoutError` из
  `getresponse()`/`read()` (с 3.10 `socket.timeout` — его псевдоним); оборвал ответ —
  `http.client.RemoteDisconnected` / `IncompleteRead`. До починки они летели мимо обоих
  `except` в `request()`, и пользователь видел traceback вместо сообщения. Теперь ветка
  сетевых повторов ловит `(URLError, TimeoutError, http.client.HTTPException)` — те же
  повторы для `GET`, то же «Сеть недоступна…», тот же `soft=True`. Шире (до `OSError`)
  брать нельзя: это общий предок и `URLError`, и `HTTPError`, и всего несетевого.
  `.reason` есть только у `URLError`, поэтому текст берётся через `getattr(e, "reason", e)`.
  Сценарии на молчащем сокете — `tools/check-retry.py`.
- ⚠ **Закрытие задачи может примениться частично.** Наблюдали `429` на `done` уже ПОСЛЕ
  записи отчёта в заметку, но ДО переноса колонки: повторный `done --report` задвоил бы
  отчёт в карточке, поэтому добивать надо `done --no-report`.
- ⚠ **Системные колонки создаются не сервером, а клиентом.** У проекта, заведённого через
  API, `KS-<pid>-TODO` / `-IN-PROGRESS` / `-DONE` есть сразу; у заведённого в приложении и
  пока пустого — их нет, пока приложение не синхронизируется (замер: `init` не нашёл их в
  14:17:34, приложение создало все три в 14:18:17, `modificatedDate` трёх — в пределах 2 мс,
  то есть одной пачкой). Создать их самому нельзя: `POST /kanban-status` с явным `id`
  отвечает ошибкой. Удалить тоже нельзя: `DELETE /kanban-status/<системная>` отвечает
  ошибкой, колонка остаётся жива (проверено на черновом проекте).
- ⚠ **`/kanban-task-status` не поддерживает `?projectId=`**: с ним отдаёт **пустой список**,
  а не отказ — фильтр, которого нет, выглядит как «связок нет». Без фильтра отдаёт связки
  всего аккаунта одним заходом; свои отбирать по `statusId`. Связка у задачи одна, её id
  детерминирован (`KTS-<taskId>`), поэтому повтор POST здесь безопасен.
- ⚠ **Привязать задачу к несуществующему `statusId` нельзя** — POST отвечает ошибкой,
  задача остаётся без колонки. Поэтому «взять системный id заранее, он всё равно появится»
  не работает.
- **Заголовок задачи может обрасти HTML — но не от REST.** В базе наблюдалось
  `<a href="http://banlist-ufm-cft.md">banlist-ufm-cft.md</a>` вместо отправленного простого
  текста. Пять контрольных проб через API вернули заголовки байт в байт: автолинковку делает
  клиент приложения при синхронизации, уже после создания. Следствие: сверять заголовок сразу
  после записи бесполезно, чистить надо на показе — и только `<a>`, потому что `<details>` и
  `<ac:structured-macro>` в заголовках бывают осмысленным текстом.
- **Таймауты — штатный режим.** Наблюдали обрыв `POST /kanban-task-status` посреди цепочки
  из восьми `add`: задача создана, колонка не привязана. GET повторять безопасно,
  `POST /task` — нет (появится второй объект), поэтому у них разная политика повторов.
- **`DELETE /v2/task/{id}` удаляет насовсем, а не помечает `removed`:** отвечает `200` с
  пустым телом, после этого `GET /v2/task/{id}` даёт `404`, задача исчезает из выборок, а
  её канбан-связка `KTS-<taskId>` пропадает вместе с ней (не остаётся с `removed=true`,
  как при удалении колонки). То же у `DELETE /v2/checklist-item/{id}`: пункт пропадает из
  списка, а не помечается удалённым.
- ⚠ **`journalDate` — это «унесено в дневник», а не «удалено».** Приложение проставляет его
  выполненным задачам (замер: `T-bb8d9b41` и `T-76f397c6` получили его в один и тот же
  момент `2026-09-11T07:50:50Z`). Задача при этом жива: `checked=1`, `removed=False`,
  связка с колонкой на месте. Отбрасывать такие наравне с `removed` нельзя — колонка
  «Готово» опустеет при живых задачах. Заведено `T-1c00aafb`.
- **Форматирование заметки.** Словарь снят с локальной базы приложения — то, что оно пишет
  само, оно гарантированно и рисует. На тексте: `bold`, `italic`, `link`,
  `singularityBackgroundAttribute`. На переводе строки (блочные): `list` =
  `bullet`/`ordered`/`checked`/`unchecked`, `header` = 2/3, `align`, `indent`.
  ⚠️ Блочный атрибут в Quill вешается на `"\n"`, а не на текст строки — перепутать легко,
  и тогда приложение покажет обычный абзац вместо списка.
- ⚠️ **В локальной базе `note` у задачи — ссылка `N-T-<taskId>`** на коллекцию `notes`
  (текст в поле `content`), а REST отдаёт содержимое прямо в поле `note`. Это разные
  представления одного и того же; расхождение между базой приложения и API само по себе
  не означает потерю данных.
- `PATCH` заметки **двигает** `modificatedDate` задачи (замер: 1789077941292 → 1789077942943),
  так что дельта-синхронизация клиента изменение видит.

## Как проверять формат поля перед тем, как его писать

**API — не свидетель по вопросу формата.** Он принимает и отдаёт обратно то, что
приложение разобрать не может: обёртка `{"ops":[...]}` в `note` проходила туда и
обратно без единой ошибки, а карточка рисовала сырой JSON. Контур «записал через API →
прочитал через API» такой класс ошибок увидеть не способен в принципе — он проверяет
хранилище, а не рендер. Независимый свидетель один: **локальная база приложения**.

### Где база

```
~/Library/Containers/ru.sibirix.singularitydesktop/Data/Library/
  Application Support/SingularityApp/
    IndexedDB/sg_renderer_0.indexeddb.leveldb/   ← живая база, НЕ ТРОГАТЬ
    nedb-backup/AppDatabase_<YYYYMMDD>_<HHMMSS>.json       ← читать это
    nedb-backup/AppDatabase_<...>.cens.json                ← НЕ читать, см. ниже
```

Приложение сандбоксовано, поэтому в `~/Library/Application Support/` его каталога
**нет** — он внутри `~/Library/Containers/ru.sibirix.singularitydesktop/`. Живая база —
LevelDB, её держит запущенное приложение; открывать её нельзя. Приложение само кладёт
рядом суточные снапшоты в JSON — работаем по самому свежему.

⚠ Соседний `*.cens.json` выглядит «безопасной обезличенной копией», но в нём буквы
заменены на `?` **включая имена ключей JSON**: `{"insert": …}` превращается в
`{"??????": …}`. Считать по нему формы нельзя — дельта перестаёт быть дельтой.

⚠ Снапшот суточный: правки, сделанные после полуночи, в нём ещё не лежат. Для проверки
формата это не мешает (форма поля не меняется за сутки), для проверки конкретной записи —
мешает.

### Чем смотреть

`tools/db-shapes.py` — он лежит **в репозитории-эталоне** скилла и в каталоги
инструментов не раскатывается, запускать из клона репозитория.
Только чтение (`open(..., "rb")`), в каталог
приложения не пишет ничего. Содержимое строк печатать не умеет намеренно: база личная, в
ней весь трекер пользователя, а скилл ограничен подпроектами «ИИ проекты» — наружу
выходят только классы значений, длины и частоты.

```bash
tools/db-shapes.py backups                 # какие снапшоты есть и насколько свежие
tools/db-shapes.py audit                   # все поля, которые пишет скилл, одним прогоном
tools/db-shapes.py fields tasks            # что вообще лежит в коллекции
tools/db-shapes.py shape tasks note tags   # частотная картина форм значения
tools/db-shapes.py values tasks priority   # распределение значений (строки — классом)
tools/db-shapes.py delta notes content     # разбор дельты: обёртка/массив, attributes
tools/db-shapes.py refs tasks note         # поле хранит значение или ссылку?
```

### Процедура

1. **До первой записи в новое поле** — `shape <коллекция> <поле>` по живым данным.
   Смотреть на **частоты**, а не на пример: одна запись ничего не доказывает, а
   «массив 720 против обёртки 0» — доказывает.
2. **Меньшинство читать, большинство писать.** Редкие формы (legacy-текст, пустая
   строка) обязаны разбираться на чтении, но писать надо только доминирующую.
3. **`refs`, если поле похоже на текст, но коротко.** `tasks.note` выглядит строкой, а
   на деле ссылка `N-<taskId>` — 100 % значений совпали с `notes.id`. Пока это не
   проверено, «строка» ничего не значит.
4. **Словарь оформления брать из `delta`, а не из документации Quill.** Приложение
   рисует своё подмножество плюс собственные ключи (`singularityColorAttribute`,
   `sx-table-*`). Ключ, которого в базе нет ни разу, — это не «поддерживается, просто не
   используется», а «не проверено».
5. **Не выводить id по шаблону, пока шаблон не посчитан.** `KS-<projectId>-TODO`
   подтверждается (24 из 24 системных колонок), `N-<containerId>` подтверждается
   (726 из 726), а `KTS-<taskId>` — нет (23 из 46) и `Q-<projectId>` — нет (9 из 56).
   Разница видна только по частоте.
6. **Расхождение с этим файлом — правим этот файл**, в том же заходе и с числами.
   Формулировка «проверено по базе, N из M» стоит дороже любой уверенности.
7. **Запись только через приложение или API.** В базу не писать ни при каких условиях:
   она боевая, приложение обычно запущено, и своя запись мимо него означает потерю
   данных при следующей синхронизации.

## MCP-сервер (оценён, не используется)

- Endpoint: `https://mcp.singularity-app.com/mcp`, требует тариф Pro/Elite.
- Авторизация: Bearer в заголовке (`bearer_methods_supported: ["header"]`),
  authorization server — `https://me.singularity-app.com`.
- Скоупы: `tasks:read|write|check`, `projects:*`, `kanban:*`, `checklists:*`,
  `habits:*`, `tags:*`, `time_stat:*`, `mcp:*`.
- Набор инструментов сужается query-параметром:
  `?toolsets=tasks,projects,kanban,tags,habits,meta,system` (группы, не данные).

**Решение: не подключаем.** Оценка 2026-09-11, карточка `T-c3070463`. Сверено фактами,
`tools/mcp-probe.py` повторяет проверку. Три независимые причины, третья решающая.

**1. REST-токен для MCP не подходит — второго пути авторизации нет.**
Токен из Keychain, которым работает `sing.py`, на `initialize` даёт `401 Unauthorized`.
Контрольный замер: заведомо мусорная строка вместо токена даёт **тот же самый** ответ —
то есть гейт MCP не распознаёт REST-токены вообще, а не «токену не хватает прав».
Одновременно `sing.py doctor` на этом же токене отвечает «токен рабочий». Гейт стоит
до JSON-RPC (nginx/Express + `www-authenticate: Bearer realm=...`), так что дело не в
обвязке запроса.

**2. В headless/cron не взлетит — это свойство сервера, а не настройки.**
`/.well-known/oauth-authorization-server` отдаёт
`grant_types_supported: ["authorization_code", "refresh_token"]`. Ни
`client_credentials`, ни device-flow: `/oauth/device_authorization` → `404`,
`/.well-known/openid-configuration` → `404`. Значит **любое** первичное получение
токена — это redirect в браузер с человеком у клавиатуры; `refresh_token` только
продлевает уже полученную сессию и сам однажды истекает. Cron-запуск не может
переавторизоваться и умрёт молча в момент, который никто не выбирал. Оговорка в
`SKILL.md` («CLI детерминирован и не зависит от OAuth-сессии») подтверждена, а не
унаследована.

**3. Ограничение области «ИИ проекты» через MCP не удержать. Это решающий довод.**
В списке скоупов нет ни одного измерения «проект» или «поддерево»: гранулярность —
тип сущности (`tasks:write`), а не объём данных. Wiki подтверждает: `toolsets` режет
**группы инструментов**, ограничения по проектам не предусмотрено. То есть выданный
MCP-токен открывает агенту весь аккаунт: сейчас в области 4 подпроекта, **вне области —
41 проект** (личное, рабочее, семейное). Сегодня ограничение держит код:
`assert_allowed()` поднимается по цепочке `parent` до корня и падает, причём вызывается
на **проекте самой задачи** (`sing.py:412`), а не только на привязке репозитория, —
`report T-<чужая>` мимо него не проходит. С MCP единственным барьером остаётся
формулировка в промпте. `AGENTS.md` §3 отдельно оговаривает, что область не вынесена
даже в переменную окружения, потому что снимается одной строкой; инструкция в промпте
слабее переменной окружения.

Что это даёт сверх REST — ничего: вендор описывает MCP как обёртку над публичным API,
таксономия скоупов один в один повторяет сущности REST v2. Обратное неверно —
`POST /v2/batch` в REST без лимита, а `system` (батч) в MCP выключен по умолчанию и
режет пачку до 20 операций.

Проверка фактом (`AGENTS.md` §4) от формы ответа tool'а не зависит: важно, что перечитывание
состояния — это **отдельный** вызов, который модель может не сделать. У `sing.py` перечитывание
зашито в `move_to_column()` (`sing.py:373`), и команда падает, если перенос не применился;
это и ловит `change-column`, отвечающий `200` вхолостую.

**Что проверить не удалось:** поимённый `tools/list` и форма ответов tool'ов — сервер не
отдаёт их без OAuth, публичного перечня нет. Нужен тариф Pro/Elite и интерактивная
авторизация в браузере. На вывод это не влияет: п. 2 и 3 следуют из метаданных
авторизации и модели скоупов, а не из состава инструментов.

**Пересмотреть, если** вендор добавит `client_credentials`/device-flow (снимет п. 2) **и**
скоуп или настройку с ограничением по проекту (снимет п. 3). Проверяется повторным
прогоном `tools/mcp-probe.py` и чтением
`/.well-known/oauth-authorization-server`.
