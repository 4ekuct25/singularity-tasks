# Правила проекта: singularity-tasks

> Это единственный файл с правилами проекта. `CLAUDE.md` в корне — заглушка `@AGENTS.md`,
> текста правил в ней быть не должно: над репозиторием работают пять разных агентов, и
> правила в двух файлах разъезжаются с первой же правки.

Этот репозиторий — **эталон** скилла `singularity-tasks`. Рабочие копии живут в каталогах
пяти инструментов и обязаны совпадать с эталоном:

| Инструмент | Каталог |
|---|---|
| Claude Code | `~/.claude/skills/singularity-tasks/` |
| Codex CLI | `~/.codex/skills/singularity-tasks/` |
| OpenCode | `~/.config/opencode/skills/singularity-tasks/` |
| Antigravity | `~/.gemini/config/skills/singularity-tasks/` |
| Qwen Code | `~/.qwen/skills/singularity-tasks/` |

⚠️ `~/.gemini/skills/` — это Gemini CLI, а не Antigravity. Antigravity читает
`~/.gemini/config/skills/`, Qwen Code — `~/.qwen/skills/`. Перепутать легко, проверять по
факту. Qwen сканирует ещё и `~/.agents/skills/`, но ставить в оба каталога нельзя: скилл
прочитается дважды и будет конкурировать сам с собой за триггеры.

**Лежит в каталоге ≠ подхвачено.** `install.sh --check` сверяет файлы и про это ничего не
говорит. У Antigravity факт проверяется командой `agy -p "/skills"` (читает каталоги и
выходит, модель не дёргается): в списке должна быть строка `singularity-tasks` с путём
`~/.gemini/config/skills/...` и `model_invocable: true`. Для остальных четырёх аналога пока
нет — там нужен запуск инструмента и вопрос «какие скиллы доступны».

Antigravity, кроме глобального каталога, сканирует рабочую копию — `.agents/skills/`
(а также `_agents`, `.agent`, `_agent`) от cwd до корня репозитория. Копию скилла в
`.agents/skills/` этого репозитория класть нельзя: она перебьёт глобальную по приоритету
и разъедется с эталоном. `.agents/singularity.json` — это привязка, не скилл, и помехой
не является.

## 1. Источник правды — здесь, не в каталогах инструментов

- **Править только файлы этого репозитория.** Правка напрямую в любом из каталогов выше
  запрещена: следующая раскатка её молча затрёт.
- После любой правки — `tools/install.sh`. Правка без раскатки не существует: агенты
  продолжат работать по старой версии, причём каждый по своей.
- Перед началом работы со скиллом — `tools/install.sh --check`. Разошлось — сначала
  разобраться, где настоящая правка, и перенести её сюда, и только потом раскатывать.
- Раскатка делает бэкап каждой цели в `~/.singularity-tasks-backup/<цель>`, путь отката
  печатается в конце. **Бэкап нельзя класть внутрь каталога скиллов**: любой каталог с
  `SKILL.md` там регистрируется как отдельный скилл, и копия начинает конкурировать с
  оригиналом за те же триггеры.
- Новый инструмент добавляется строкой в `TARGETS` внутри `tools/install.sh`.

**Два правила выше держатся механизмом, а не памятью.** Помнить их не надо — и не стоит:
как правило они уже существовали и не сработали ни разу, потому что правку помнят, а
раскатку нет.

- `sing.py start` и `sing.py done`, запущенные **внутри этого репозитория**, сверяют
  установленные копии с рабочим деревом и печатают предупреждение, если они разошлись.
  Сверка локальная (сравнение файлов, без сети, ~0,1 с), при совпадении **не печатает
  ничего** и никогда не роняет команду. В любом другом репозитории она не срабатывает.
  Общий примитив сверки — `tools/install.sh --check --quiet`: код 1 и список разошедшихся
  целей одной строкой, при совпадении пусто. Логика сверки живёт в одном месте.
- Предупреждение **не раскатывает ничего само**. Расхождение значит одно из двух — правка
  не раскатана либо база рабочего дерева устарела; действия разные, выбирает человек.
- Отключается на один запуск: `SINGULARITY_NO_SYNC_CHECK=1`. Явно и на виду, потому что
  гейт без легального обхода обходят нелегально.

⚠️ **Из git worktree `tools/install.sh` раскатывать отказывается** (код 2). Раскатка
перезаписывает общие каталоги пяти инструментов целиком — из worktree туда уехала бы
отдельная ветка вместе с незакоммиченным, поверх работы параллельных сессий. Сверять
(`--check`) из worktree можно и нужно, предупреждение в worktree так и говорит: не
раскатывай отсюда. Раскатка — после слияния, из основного рабочего каталога; `--force`
существует, но это осознанное решение, а не способ обойти отказ.

Синхронизируются: `SKILL.md`, `README.md`, `scripts/`, `references/`.
Не синхронизируются и живут только здесь: `AGENTS.md`, `CLAUDE.md`, `JOURNAL.md`,
`tools/`, `tests/`, `.claude/`.

`tests/` не раскатывается сознательно: агент, работающий по скиллу, их не запускает,
а живые проверки создают и удаляют проекты в трекере пользователя — им не место в
каталоге, откуда скилл подхватывается автоматически.

## 2. Кто что читает

| Файл | Аудитория | Назначение |
|---|---|---|
| `SKILL.md` | модель | инструкция агенту: процедура, правила колонок, ограничения |
| `README.md` | человек | установка, подключение репозитория, команды, диагностика |
| `references/api.md` | модель и человек | API, форматы, известные ловушки |
| `scripts/sing.py` | обе | вся логика |

Меняешь поведение — правь и код, **и** тот файл, который его описывает. Расхождение кода и
документации здесь дороже обычного: по SKILL.md агент действует буквально.

## 3. Область работы

Скилл жёстко ограничен подпроектами проекта **«ИИ проекты»** — константа
`ROOT_PROJECT_TITLE` в `scripts/sing.py`. Это не настройка: переменной окружения
намеренно нет, иначе ограничение снимается одной строкой.

Расширять область — отдельное осознанное решение, а не побочный эффект задачи. Просьбу
«поработай с задачей из другого проекта» выполнять нельзя: проект переносится под
«ИИ проекты» руками.

## 4. Проверять фактом, а не кодом ответа

API этого сервиса умеет отвечать `200`, ничего не сделав (`change-column` на системных
колонках — ровно такой случай). Поэтому:

- **любая операция, меняющая состояние, обязана перечитать состояние и сверить его**, а не
  докладывать об успехе по HTTP-статусу;
- «проверка» одним запросом, который в принципе не может показать сбой, — не проверка;
- прогонять надо ту конфигурацию, что в бою: проверка на своих колонках ничего не говорит
  о системных, они ведут себя иначе.

Каждое изменение скилла проверяется на живом API, а не только компиляцией.

Регрессионный набор — `tests/run.py` (быстрые без сети и без токена, живые на
черновом `zz-`-подпроекте). После правки `scripts/sing.py` — как минимум
`tests/run.py fast`; если правка трогает работу с трекером — ещё и `live`.
Новая проверка обязана уметь краснеть: сломай поведение намеренно и убедись,
что набор это ловит, — иначе в наборе прибавилось строк, а не смысла.

## 4.1. Что лежит в `tools/` и когда это запускают

Инструменты накапливаются после каждого расследования и через месяц неотличимы друг от
друга. Чтобы набор оставался читаемым: **новый скрипт в `tools/` — строка в этой таблице
в том же коммите.** Скрипт, чью работу перехватил `tests/`, — удалить, а не оставлять
«на всякий случай»: два источника правды на одну проверку расходятся, и непонятно, какому
верить.

| Инструмент | Когда запускают |
|---|---|
| `install.sh` | после любой правки скилла; `--check` — перед началом работы |
| `audit-secrets.sh` | перед каждым commit (staged) и push (`--push`, диапазон) |
| `zz-project.py` | черновой `zz-`-подпроект для живых проверок; зовётся из `tests/` |
| `check-retry.py` | политика повторов на локальной заглушке; зовётся из `tests/run.py` |
| `db-shapes.py` | выяснить, в каком виде приложение РЕАЛЬНО хранит поле (см. §4) |
| `check-today-link.py` | выбор связки: доска проекта против системной «Сегодня» |
| `check-claim-race.py` | воспроизвести гонку захвата: несколько агентов на одну задачу |
| `fix-split-board.py` | починка живых данных при симптоме «доска раздвоена» |
| `watch-tags.py` | расследование пропажи `agent:*`-тегов (карточка ещё открыта) |
| `mcp-probe.py` | пересмотр решения по MCP — условия пересмотра в `references/api.md` |
| `paging-loadtest.py` | гейт полноты выборки под нагрузкой после правок `paged()` |
| `count-requests.py` | цена команды в запросах и секундах после правок `board`/`list` |
| `qwen-trace.py` | разбор стенограммы Qwen: как живой агент пользовался скиллом |
| `note-format-audit.py` | доля «стен» в записях агентов: до и после правок формата записи в карточку |

Четыре последних постоянного места в `tests/` не имеют: они меряют, а не утверждают, и
запускаются руками под конкретный вопрос.

## 5. Секреты

Токен живёт в macOS Keychain (`-s singularity-app -a rest-token`) — он общий для всех
пяти инструментов. В репозитории его нет и быть не может. `singularity.json` секретов
не содержит: там только id проекта и колонок, его можно коммитить.

Привязка репозитория ищется в `.agents/`, затем `.claude/`, затем в корне. Новые
репозитории получают нейтральный `.agents/singularity.json` — привязка не должна лежать
в каталоге одного конкретного инструмента, если скилл работает во всех пяти.

Перед тем как что-либо уедет из репозитория — `tools/audit-secrets.sh`:

```bash
tools/audit-secrets.sh              # перед commit (staged)
tools/audit-secrets.sh --push       # перед push: <upstream>...HEAD, не staged
tools/audit-secrets.sh --range A..B
```

⚠ Перед push проверять **диапазон**, а не staged: `git diff --cached` покрывает только
незакоммиченное, и при чистом дереве гейт на staged не проверит ничего. Поэтому пустой
ввод скрипт считает ошибкой (код 2), а не «чисто» — молчаливое «ок» на пустом диффе и
есть способ пропустить секрет.

Идентификаторы сущностей трекера (`P-`/`KS-`/`T-`/`A-`/`Q-`/`KTS-`/`N-` + uuid) из
UUID-проверки исключены намеренно: без токена они ничего не открывают, а гейт, который
краснеет на каждом коммите, перестают читать.

## 6. Тестовые данные убирать за собой

Проверки идут на живом трекере пользователя. Всё созданное для проверки — задачи, секции,
заметки, теги, колонки — удаляется в том же заходе. Доска после работы обязана выглядеть
так же, как до неё, плюс осмысленный результат.

Колонки не удалять, пока в них есть задачи: задача осиротеет и пропадёт с доски.

## 7. Журнал

Осмысленные изменения — в `JOURNAL.md`, сверху новые. Одна запись = одно изменение:
что, почему, как проверено (с числами и фактами, не «ок»), как откатить. Наблюдение,
объясняющее, **почему код такой** (поведение API, реакция сервера), пишется даже если
правки кода не было — именно оно теряется между сессиями.
