# singularity-tasks

Скилл, через который ИИ-агенты берут задачи из [SingularityApp](https://singularity-app.ru/)
и отчитываются о работе прямо в трекере.

Идея простая: вы накидываете задачи в очередь проекта, агент забирает верхнюю, двигает
карточку по канбан-доске и пишет в неё отчёт. Прогресс видно в обычном приложении — ничего
не нужно выспрашивать в чате.

- `SKILL.md` — инструкция для агента (её читает модель, не вы)
- `scripts/sing.py` — CLI поверх REST API v2, только stdlib
- `references/api.md` — справочник по API и подводные камни

Формат SKILL.md общий, поэтому один и тот же скилл работает в пяти инструментах:

| Инструмент | Куда ставится |
|---|---|
| Claude Code | `~/.claude/skills/singularity-tasks/` |
| Codex CLI | `~/.codex/skills/singularity-tasks/` |
| OpenCode | `~/.config/opencode/skills/singularity-tasks/` |
| Antigravity | `~/.gemini/config/skills/singularity-tasks/` |
| Qwen Code | `~/.qwen/skills/singularity-tasks/` |

⚠️ Каталоги легко перепутать: `~/.gemini/skills/` — это **Gemini CLI**, Antigravity читает
`~/.gemini/config/skills/`, а Qwen Code — `~/.qwen/skills/`. Qwen сканирует ещё и общий
`~/.agents/skills/`, но копия ставится только в один каталог: из двух он прочитал бы скилл
дважды и показал два одинаковых описания с теми же триггерами.

Раскатка во все установленные инструменты — одной командой из репозитория-эталона:

```bash
tools/install.sh --list    # куда поставится и что установлено сейчас
tools/install.sh --check   # разошлось ли установленное с эталоном
tools/install.sh           # раскатать (с бэкапом и путём отката)
```

Инструменты, которых нет на машине, пропускаются. После раскатки сессии агентов надо
перезапустить, чтобы они перечитали список скиллов.

**Забыть раскатать правку нельзя молча.** Внутри этого репозитория `sing.py start` и
`sing.py done` сами сверяют установленные копии с рабочим деревом и печатают
предупреждение, если они разошлись. Сверка локальная (сравнение файлов, без сети,
~0,1 с), при совпадении не печатает ничего и никогда не роняет команду. Подробности —
[«Проверка синхронизации»](#проверка-синхронизации-эталона) ниже.

⚠️ Из **git worktree** `tools/install.sh` раскатывать отказывается: он залил бы в общие
каталоги пяти инструментов содержимое отдельной ветки, включая незакоммиченное, поверх
работы параллельных сессий. Сверять из worktree можно (`--check`), раскатывать — после
слияния из основного рабочего каталога, либо осознанно через `--force`.

**Файл в каталоге ≠ инструмент его подхватил.** `--check` сверяет только файлы; то, что
инструмент прочитал скилл и показывает его модели, — отдельный факт, и проверять его надо
отдельно. У Antigravity для этого есть команда, которая не поднимает чат и не обращается к
модели (`num_turns: 0`, нулевой расход токенов):

```bash
agy -p "/skills" | cut -f1                 # имена всех видимых скиллов
agy -p "/skills" --output-format json      # плюс path, builtin, model_invocable
```

В выводе должна быть строка `singularity-tasks` с путём
`~/.gemini/config/skills/singularity-tasks/SKILL.md`, `"builtin": false` и
`"model_invocable": true` — последнее и означает «модель может это вызвать».

> **Область работы жёстко ограничена подпроектами проекта «ИИ проекты».**
> Остальной трекер для агента не существует. Ограничение — константа
> `ROOT_PROJECT_TITLE` в `scripts/sing.py`, проверяется при каждой операции.

## Установка

### 1. Токен

`me.singularity-app.com` → раздел API → **Создать токен**. Права:

| Тип | Чтение | Запись |
|---|---|---|
| Задача | ✅ | ✅ |
| Канбан-доска | ✅ | ✅ |
| Чек-лист | ✅ | ✅ |
| Тег | ✅ | ✅ |
| Проект | ✅ | только если `init` должен создавать проекты |
| Группа задач | ✅ | если пользуетесь секциями |

Остальное (привычки, статистика таймеров, заметки) скиллу не нужно.

### 2. Положить токен в Keychain

```bash
security add-generic-password -s singularity-app -a rest-token -w
```

Значение у `-w` намеренно опущено — токен спросят скрытым вводом, и он не попадёт в
историю шелла. Обновить существующий токен — тот же вызов с `-U` (без него `security`
скажет, что запись уже есть).

В репозиторий токен не кладём никогда. Альтернативы Keychain: переменная
`SINGULARITY_TOKEN` или файл `~/.claude/.singularity-token` с правами `600`.

### 3. Проверить связь

```bash
python3 ~/.claude/skills/singularity-tasks/scripts/sing.py doctor   # или любой другой каталог из таблицы ниже
```

`doctor` проверяет только чтение. Токен может быть выдан read-only — тогда всё сломается
позже, на первом `start`, посреди работы. Проверить права на запись сразу, после
привязки репозитория:

```bash
sing.py doctor --write
```

Он создаёт в привязанном проекте пробную задачу, по шагам проверяет запись (PATCH,
перенос по колонкам с возвратом, чек-лист, complete/uncomplete) и удаляет пробу в том же
заходе — доска после прогона выглядит ровно как до него. Каждый шаг проверяется
перечитыванием состояния, а не кодом ответа. Если хоть один шаг не прошёл, команда
выходит с кодом 1 и печатает, что именно не прошло.

Дальше в примерах `sing.py` — сокращение этого пути. Удобно завести алиас:

```bash
alias sing='python3 ~/.claude/skills/singularity-tasks/scripts/sing.py'
```

## Подключение репозитория к проекту

Один раз на репозиторий. Проект должен лежать внутри «ИИ проекты» — если его там нет,
создайте или перенесите в приложении.

```bash
cd ~/Projects/мой-репозиторий
sing.py projects                                  # что доступно
sing.py init --project "мой-репозиторий"          # план, ничего не меняет
sing.py init --project "мой-репозиторий" --apply  # выполнить
```

`init` без `--apply` — **сухой прогон**: печатает, какие колонки создаст и какие
переиспользует. Это изменение вашего живого трекера, поэтому по умолчанию он ничего не
трогает.

Результат — файл `<repo>/.agents/singularity.json` с id проекта и колонок. Секретов в нём
нет, его можно и нужно коммитить: тогда любой агент, зашедший в репозиторий, сразу знает,
куда смотреть.

Про колонки: `Новые`, `В работе`, `Готово` — системные колонки проекта, они уже есть у
каждого проекта и переиспользуются. `На проверке` и `Заблокировано` скилл создаёт сам.

## Как пользоваться

### Вы

Кидаете задачи в колонку **«Новые»** — из приложения, телеграм-бота, откуда удобно.
Всё, что там лежит, агент считает разрешённым к работе. Приоритет задачи определяет
очередь: высокий разбирается первым.

Смотрите результат там же. Карточка ведёт себя как история: при взятии в неё пишется
`ПЛАН` — что агент собрался делать, при закрытии `РЕЗУЛЬТАТ` — что изменено, чем проверено,
каким коммитом. Обе записи обязательны, команда без них откажет. Разошлись план и
результат — значит, по дороге выяснилось что-то новое, и это видно.

### Агент

Обычно достаточно сказать «возьми задачу» — скилл подхватится сам. Под капотом:

```bash
sing.py board                     # что на доске и кто что держит (@имя слева)
sing.py next                      # верхняя задача очереди
sing.py start T-... --plan "..." # → «В работе» + тег + план в карточку
sing.py report T-... "текст"      # промежуточный факт в карточку
sing.py done T-... --report "..." # → «Готово» + отметка выполнения
sing.py done T-... --review       # если нужен ваш взгляд
sing.py block T-... "причина"     # → «Заблокировано»
sing.py release T-...             # передумал: вернуть в очередь, сняв свой тег
```

Правила, которых агент обязан держаться, описаны в `SKILL.md`. Главные: колонка меняется
**до** начала работы, одна задача в работе на агента, и сессия не заканчивается задачей,
брошенной в «В работе».

### Несколько агентов

`start` вешает на задачу тег `agent:<имя>` — видно, кто именно ведёт карточку. Имя
задаётся переменной окружения в окружении конкретного агента:

```bash
export SINGULARITY_AGENT=codex
sing.py whoami                        # под каким тегом я работаю
sing.py list --column wip --mine      # что в работе именно у меня
```

⚠️ Одновременный `next` у двух агентов пока может отдать им одну задачу — гонка не
закрыта, она заведена отдельной задачей в бэклоге. Пока агентов больше одного, разводите
их по секциям (`next --group`).

## Секции и заметки

**Секции** режут проект по направлениям и не связаны с колонками — задача одновременно
лежит в секции и стоит в колонке.

```bash
sing.py groups                                   # секции и сколько в каждой открытых
sing.py groups --create "Инфра"
sing.py add "Задача" --group "Инфра"
sing.py next --group "Инфра"                     # брать только своё направление
```

**Заметки проекта** — долгоживущий контекст, который агент читает перед работой: как
разворачивается прод, что не трогать, какие есть договорённости. На доску не попадают и
в очередь задач не лезут.

```bash
sing.py notes
sing.py notes --add "Контекст" --text "Прод разворачивается через ansible."
```

## Команды

| Команда | Что делает |
|---|---|
| `doctor` | токен, привязка репо, живы ли колонки, дубли на доске; `--write` — ещё и права на запись (пробная задача создаётся и удаляется здесь же) |
| `projects` | доступные проекты (только внутри «ИИ проекты») |
| `init` | привязать репозиторий к проекту; без `--apply` — сухой прогон |
| `board` | доска по колонкам, слева `@имя` держателя по тегам `agent:*`; `--limit` — сколько закрытых показывать |
| `next` | верхняя задача очереди; `--group`, `--json` |
| `list` | задачи в колонке; `--column`, `--group`, `--mine` |
| `show` | карточка задачи с заметкой |
| `start` | взять в работу: записать план (`--plan`, обязателен), колонка, agent-тег |
| `report` | дописать отчёт в заметку |
| `done` | закрыть с результатом (`--report`, обязателен); `--review` — на проверку вместо закрытия |
| `block` | пометить заблокированной с причиной |
| `release` | вернуть задачу в очередь: снять свой тег, отметку выполнения и колонку |
| `add` | создать задачу или подзадачу; `--note` обязателен (`--no-note` — осознанно без описания), плюс `--parent`, `--group`, `--priority`, `--deadline` |
| `move` | переставить задачу в колонку и больше ничего не менять — починка доски |
| `rm` | удалить задачу (`--yes` обязателен) — уборка за собой после проверок |
| `checklist` | добавить пункты чек-листа |
| `groups` | секции проекта; `--create` |
| `notes` | заметки проекта; `--add` + `--text` |
| `whoami` | под каким agent-тегом работает текущий агент |

## Проверка синхронизации эталона

Скилл живёт в репозитории-эталоне, а агенты работают с копиями, разложенными по каталогам
пяти инструментов. Правка, не раскатанная `tools/install.sh`, не существует: пять агентов
продолжают работать по старой версии, причём каждый по своей. Помнить об этом не нужно —
проверка встроена в рабочий цикл:

- **`sing.py start` и `sing.py done`**, запущенные внутри репозитория-эталона, сверяют
  установленные копии с рабочим деревом и предупреждают, если они разошлись. Это два
  момента, когда расхождение ещё можно отработать: перед первой правкой и при закрытии
  задачи. В любом другом репозитории проверка не срабатывает — сверять там нечего.
- Сверка **локальная**: сравнение файлов, ни одного сетевого запроса, ~0,1 с рядом с
  командой, которая и так ходит в API.
- При совпадении **не печатает ничего** и никогда не роняет команду: если сама сверка не
  сработала, задача важнее.
- Раскатку она **не запускает** — только предупреждает. Расхождение значит одно из двух:
  правка не раскатана либо база рабочего дерева устарела, и разбираться с этим надо
  по-разному.

```bash
tools/install.sh --check           # что именно разошлось, с диффом
tools/install.sh --check --quiet   # только имена разошедшихся целей; молчит при совпадении
SINGULARITY_NO_SYNC_CHECK=1 sing.py done T-...   # отключить предупреждение на один запуск
```

Расхождение найдено — **сначала понять, где настоящая правка**. Если её сделали прямо в
каталоге инструмента (так делать нельзя, но так делают), сначала перенести её в
репозиторий: раскатка перезаписывает цели целиком и такую правку молча потеряет.

## Если что-то не так

| Симптом | Причина и что делать |
|---|---|
| `401 Unauthorized` | токен отозван или урезан. Права у токена не редактируются — пересоздать |
| `✗ запись прошла N из 6 проверок` (`doctor --write`, код 1) | токену не хватает прав на запись — пересоздать с записью на «Задача», «Канбан-доска», «Чек-лист» |
| `ПРОБА ОСТАЛАСЬ НА ДОСКЕ: T-…` | уборка пробы не отработала (нет прав на удаление) — удалить задачу руками |
| `ЗАПРЕЩЕНО: ... лежит вне «ИИ проекты»` | проект вне области. Перенести его под «ИИ проекты» в приложении |
| `КОЛОНКА ПРОПАЛА В ТРЕКЕРЕ` | колонку удалили или переименовали руками → `init --apply` |
| `Свободных задач нет` (код 2) | очередь пуста. Это нормальный исход, не ошибка |
| `⚠ доска раздвоена` / `⚠ КОЛОНКИ МИМО ПРИВЯЗКИ` | рядом с колонками скилла живут системные. Починка — `tools/fix-split-board.py` (сухой прогон, затем `--apply`) |
| `Канбан проекта ещё не развёрнут` при `init` | системных колонок в проекте пока нет. Открыть проект в приложении или завести в нём любую задачу, дать синхронизироваться, повторить `init` |
| `⚠ ВНЕ КОЛОНОК` в `board` | задача есть, на доске не видна: заведена мимо канбана либо `add` оборвался после создания. Починка — `move T-... <роль>` |
| `СОЗДАНА, но осталась без колонки` | сеть оборвала привязку. Задача уже существует — не повторять `add` (будет дубль), а выполнить названный в сообщении `move` |
| агент не предлагает скилл, хотя файлы на месте | проверить не каталог, а список самого инструмента: у Antigravity — `agy -p "/skills"`; нет строки `singularity-tasks` → скилл лежит не в том каталоге либо сессию не перезапускали |
| `⚠ установленные копии скилла разошлись` | правка не раскатана либо база дерева устарела → `tools/install.sh --check`, затем `tools/install.sh` |
| `Отказ: это git worktree` | раскатка из worktree затрёт общие каталоги веткой. Раскатывать после слияния из основного каталога |

### Раздвоенная доска

Системные колонки («Новые», «В работе», «Готово») появляются у проекта, заведённого в
приложении, не сразу — приложение досоздаёт их при первой синхронизации. `init`, отработавший
до этого момента, создаёт свои, и потом на доске оказываются две «В работе» и две «Готово».
Удалить системные нельзя, поэтому чинится в обратную сторону:

```bash
tools/fix-split-board.py            # что не так и что будет сделано
tools/fix-split-board.py --apply    # задачи → на системные, привязка → на них, свои удалить
```

Свежий `init` до такого состояния уже не доводит: без системных колонок он отказывается
работать и объясняет, что сделать.

Технические подробности API, формат заметок и список известных ловушек —
`references/api.md`.
