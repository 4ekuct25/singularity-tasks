# singularity-tasks

Трекер — источник правды по тому, что делается в репозитории. Человек накидывает
задачи в колонку очереди («Новые»), агент забирает их оттуда, двигает по доске и
отчитывается в карточке. Никакой параллельной пометки в чате: если задача не
отражена на доске — её как будто не было.

Инструмент: `scripts/sing.py` поверх REST API v2 (`https://api.singularity-app.com/v2`).
Он же работает в headless/cron-сессиях, где MCP-подключение недоступно.

## Доска — первое действие

**Репозиторий привязан к проекту (`.agents/singularity.json` или `.claude/singularity.json`)
— значит `sing.py board` идёт до работы, а не после.** До любых правок, до планирования, до
первого файла. Это относится и к тому, что задачей не выглядит: разбор поведения API,
наблюдение за другим агентом, «просто посмотрю». Всё это — работа, и у неё есть карточка.

Цена нарушения замерена, а не выдумана. В сессии, где скилл чинили час без карточки,
**в очереди уже лежали три задачи ровно про эту работу** — с формулировками и приоритетами.
Их не увидели, потому что не посмотрели: сделали то же самое вслепую, хуже сформулированным,
и закрывать пришлось задним числом через `--no-plan`, оставив карточки без ответа на
«что собирались». Потеряна не отчётность, а чужая уже проделанная работа по постановке.

Механизмом это правило не подпирается: никакой код не сработает раньше, чем агент вызовет
первую команду. Поэтому оно здесь первым и держится дисциплиной. Подпирается только
следствие — `add` не даёт молча завести дубль уже существующей задачи.

Порядок в привязанном репозитории:

1. `board` — что вообще есть, что уже занято, нет ли предупреждений;
2. работа из очереди — `next` / `start`; работа не из очереди — сначала `add`, потом `start`;
3. правки — только после `start`.

## «Работай по доске» — что делать по этой фразе

Человек говорит только это. Всё остальное — твоя работа, переспрашивать «какую задачу
взять» не нужно: очередь и есть ответ.

Цикл, по одной задаче за раз:

1. `sing.py board` — посмотреть, что есть и не держит ли кто-то уже задачу.
2. `sing.py next` — верхняя из очереди. Пусто (код 2) — сказать человеку, что очередь
   пуста, и **остановиться**; не выдумывать себе работу.
3. Прочитать карточку целиком (`next` печатает заметку и чек-лист). В ней обычно уже
   есть постановка, критерий готовности и первый шаг — читай их, а не начинай думать
   заново.
4. `sing.py start <id> --plan "…"` — два-три пункта по существу. **До первой правки.**
5. Сделать. Промежуточные находки — `report`, они дешевле, чем восстанавливать ход мысли
   в конце.
6. Закрыть: `done --report "…"` (сделано и проверено) либо `done --review --report "…"`
   (нужен взгляд человека). Упёрся — `block <id> "чем именно мешает"`. Задача оказалась
   не той — `release <id> --report "почему"`.
7. Коротко доложить человеку результат и **перейти к следующей задаче** — с пункта 2.

Когда остановиться и отдать ход человеку:

- очередь пуста;
- задача требует его решения — тогда `done --review`, а не догадка за него;
- упёрся в доступ, чужую систему или неоднозначную постановку — `block` с причиной;
- что-то в работе выглядит опасным или необратимым (удаление данных, правка прода).

Чего по этой фразе делать **не** надо: спрашивать разрешения на каждую задачу, брать
вторую, не закрыв первую, и заканчивать сессию с задачей в «В работе».

## Жёсткое ограничение области

**Скилл работает только с подпроектами проекта «ИИ проекты».** Всё остальное в аккаунте —
личное, рабочее, семейное — для агента не существует. Сам корневой проект рабочим быть не
может: задачи ведутся в его подпроектах.

Ограничение проверяется на каждой операции, а не один раз при привязке:

- `projects` показывает только подпроекты корня, остальные скрыты;
- `init` не найдёт проект вне области; если проект с таким названием существует снаружи —
  это отказ, а не повод создать одноимённый внутри; новый проект создаётся сразу с
  `parent` = корень;
- любая команда над задачей проверяет **проект самой задачи**, а не только привязку репо —
  иначе `report T-<чужая>` уходил бы мимо ограничения;
- отредактированный руками или принесённый из другого репозитория
  `singularity.json` не помогает: область проверяется по факту, при каждом запуске.

Ограничение задано константой `ROOT_PROJECT_TITLE` в `scripts/sing.py`, а не переменной
окружения — переменную можно выставить одной строкой, и ограничение перестанет быть
ограничением. Менять область — осознанная правка скилла, а не настройка запуска.

## Перед первым запуском

1. Токен: `me.singularity-app.com` → API → Create Token. Права: «Задача», «Канбан-доска»,
   «Чек-лист», «Тег» — чтение и запись; «Проект» — чтение (запись нужна, только если
   `init` должен создавать проект); «Группа задач» — если пользуетесь секциями.
2. Положить в Keychain (в репозиторий токен не кладём никогда):
   ```bash
   security add-generic-password -s singularity-app -a rest-token -w '<ТОКЕН>'
   ```
   Обновить существующий — тем же вызовом с флагом `-U` (без него `security` ругается,
   что запись уже есть). Значение у `-w` можно опустить: тогда токен вводится скрыто и
   не осядет в истории шелла.
3. Проверить: `python3 <каталог-скилла>/scripts/sing.py doctor`
4. Проверить, что токен не read-only: `sing.py doctor --write` (после привязки
   репозитория). Обычный `doctor` подтверждает только чтение, и урезанный токен
   всплывёт лишь на первом `start` — посреди работы.

Официальный MCP-сервер (`https://mcp.singularity-app.com/mcp`) **оценён и отклонён**:
токен из Keychain он не принимает, headless-способа авторизации у него нет
(только `authorization_code`/`refresh_token`), а главное — ограничить его областью
«ИИ проекты» нечем: скоупы гранулярны по типу сущности, не по проекту, и токен открыл
бы весь аккаунт. Разбор с фактами — `references/api.md`.

## Привязка репозитория к проекту

Одноразово на репозиторий. `init` по умолчанию **сухой прогон**: печатает план и ничего
не меняет в трекере — это изменение живой системы пользователя, применять только после «ок».

```bash
sing.py init --project "Название проекта"          # план
sing.py init --project "Название проекта" --apply  # выполнить
```

Пишет `<repo>/.agents/singularity.json` — id проекта и колонок. Секретов не содержит,
коммитится вместе с репо. Каталог `.agents/` нейтрален: скилл работает в Claude Code,
Codex, OpenCode, Antigravity и Qwen Code, и привязка не должна лежать в каталоге одного
из них.
Старые репозитории с `.claude/singularity.json` продолжают читаться, `init` их не
переносит и второй файл не заводит. Роли колонок: `todo`, `wip`, `review`, `done`, `blocked`.

Что переиспользуется, а что создаётся:

- `todo`, `wip`, `done` — **системные колонки проекта** («Новые», «В работе», «Готово»),
  id детерминированный: `KS-<projectId>-TODO` / `-IN-PROGRESS` / `-DONE`.
- `review`, `blocked` — системных аналогов нет, создаются («На проверке», «Заблокировано»)
  и встают по порядку между «В работе» и «Готово» / после неё.

⚠️ **Системные колонки есть не всегда.** У проекта, заведённого через API, они появляются
сразу; у заведённого в приложении и пока пустого — их нет, и приложение досоздаёт их позже,
при первой синхронизации. Наблюдали на живой сессии: `init` в 14:17:34 не нашёл системных и
создал пять своих, в 14:18:17 приложение добавило свои три — на доске стало восемь колонок,
две «В работе» и две «Готово» с одинаковым порядком.

Поэтому `init` **отказывается работать**, если системных колонок нет: открой проект в
приложении (или заведи в нём любую задачу), дай синхронизироваться и повтори. Осознанно
хочешь свои колонки вместо системных — `--own-columns`, и доска раздвоится ожидаемо.

Починить уже раздвоенную доску: `tools/fix-split-board.py` (в репозитории-эталоне). Сами
системные колонки удалить нельзя — `DELETE` по ним отвечает ошибкой, колонка остаётся;
чинится в другую сторону — переездом задач на системные и удалением своих.

После `init --apply` полезно глянуть `doctor` — он ругается и на колонки-тёзки, и на случай,
когда системная колонка роли жива, а скилл под эту роль держит другую.

## Рабочий цикл

```bash
sing.py board                    # что вообще на доске и кто что держит
sing.py next                     # взять верхнюю задачу очереди (приоритет → дедлайн → возраст)
sing.py start T-... --plan "..." # → «В работе» + тег + ПЛАН в карточку, ДО начала правок
sing.py list --column wip --mine # что в работе именно у меня
sing.py report T-... "текст"     # промежуточный факт в карточку
sing.py done T-... --report "..." # → «Готово» + РЕЗУЛЬТАТ в карточку + отметка выполнения
sing.py done T-... --review      # если результат требует проверки человеком
sing.py block T-... "причина"    # → «Заблокировано», причина в карточке
sing.py release T-... --report "..."  # вернуть в очередь и снять свой тег
sing.py start T-...              # он же снимает блокировку: возвращает из «Заблокировано» в работу
sing.py board --limit 20         # больше закрытых в колонке «Готово»
sing.py move T-... todo          # починка: поставить задачу в колонку, ничего больше не трогая
sing.py rename T-... "заголовок" # переформулировать карточку, не трогая ничего больше
sing.py rm T-... --yes           # убрать за собой тестовую задачу
```

**Задача заводится с описанием.** `add` требует `--note`: что сделать, критерий готовности,
где смотреть. Заголовок виден на доске целиком, карточка нужна ради подробностей — без них
человек у доски не может решить, браться ли. Наблюдение с живой сессии: из 11 вызовов `add`
ни один не пришёл с `--note`, и очередь встала голыми заголовками. Заголовок исчерпывает
задачу — явно `--no-note`.

**Форматирование в карточке работает** — заметка это Quill-delta. Ярлыки `ПЛАН`, `РЕЗУЛЬТАТ`,
`БЛОКЕР` скилл пишет жирным сам; строки текста, начинающиеся с `- `, становятся маркированным
списком. Поэтому отчёт из нескольких фактов стоит писать списком, а не одним абзацем:

```bash
sing.py done T-... --report "19/19 сьютов, 267/267 ассертов.
- FR12: details → expand исполняется
- Admin settings: PUT/GET, валидация, дефолты
- Baseline-15: одно ожидаемое падение, закрыто новым jar"
```

⚠️ **Не склеивать несколько меняющих состояние вызовов через `&&`.** Наблюдали цепочку из
восьми `add`: шестая упала по таймауту уже после `POST /task`, цепочка оборвалась, а на
доске осталась задача без колонки — и следующий заход создал её заново. Один вызов, меняющий
состояние, — одна команда оболочки; результат каждой читать, а не полагаться на общий код
возврата (посторонний `cat` в конце цепочки красит в «ошибку» весь успешный `start`).

**Закрытые задачи приложение уносит в дневник** (ставит `journalDate`), и из обычной
выборки API они пропадают. `board` запрашивает их отдельно и показывает в «Готово» с
пометкой `(в дневнике)` — история сделанного не теряется, иначе агент заведёт заново
уже закрытую задачу. В работу такие задачи не берутся: `next` и `list` их не отдают,
дневник — не очередь.

## Правила работы с колонками

Колонка — **единственный** признак статуса задачи. Не дублировать статус словами в чате
и не держать его в заметке: расходятся мгновенно, верить всё равно будут доске.

| Колонка | Что означает | Кто кладёт | Куда уходит дальше |
|---|---|---|---|
| `todo` «Новые» | очередь: сформулировано, но не начато | человек; агент — только найденное попутно | `wip` |
| `wip` «В работе» | прямо сейчас кто-то делает, тег `agent:*` показывает кто | агент, командой `start` | `review`, `done`, `blocked`, назад в `todo` |
| `review` «На проверке» | сделано, но нужно решение или проверка человека | агент, `done --review` | человек: закрывает или возвращает в `todo` |
| `done` «Готово» | сделано и проверено, стоит отметка выполнения | агент, `done` | никуда |
| `blocked` «Заблокировано» | работа упёрлась, причина записана в карточку | агент, `block` | `wip` через `start`, когда блокер снят |

Обязательное:

0. **`board` — до работы, а не после.** См. «Доска — первое действие» в начале. Пропуск
   этого шага стоит не отчётности, а чужой постановки: очередь уже может содержать ровно
   ту задачу, которую собираешься делать вслепую.
1. **`start` — первое действие, до любых правок.** Иначе на доске не видно, что задача
   занята, и параллельная сессия возьмёт её же. Не «сделаю и потом отмечу».
2. **План — обязателен, результат — обязателен.** `start` требует `--plan`, `done` требует
   `--report`; без них команда откажет. Карточка должна отвечать на два вопроса: что
   собирались сделать и что вышло. Расхождение между ними — само по себе полезный сигнал:
   значит, по дороге выяснилось что-то, чего не знали в начале, и это стоит объяснить.
   План — два-три пункта по существу, не пересказ заголовка. Задача на одно движение —
   `--no-plan` / `--no-report`, но это осознанный выбор, а не способ не думать.
   Требование держится с обеих сторон: `done` по задаче, которую не брали через `start`
   (нет ни `ПЛАН` в карточке, ни колонки `wip`), тоже откажет. Раньше это был штатный
   обход — задача уезжала из `todo` сразу в `done` с результатом, но без плана.
3. **Одна задача в `wip` на агента.** Взял вторую — первая либо закрыта, либо
   `block`, либо возвращена в `todo` с отчётом. Две карточки с одним `agent:*` в `wip` —
   это потерянный контекст, а не параллельная работа.
4. **Не заканчивать сессию с задачей в `wip`.** На выходе она обязана быть в `done`,
   `review`, `blocked` или назад в `todo` — с `report`, объясняющим, на чём остановились.
5. **`done` — только сделано И проверено.** Сомневаешься, нужен ли взгляд человека, —
   `done --review`, не `done`. Частично сделано — `report` и оставить в `wip`.
6. **Возврат в `todo` — законный ход,** если задача оказалась не той, не воспроизводится
   или требует переформулировки. Только командой `release`: она снимает отметку
   выполнения, свой `agent:*` тег и ставит колонку. Ручной перенос колонки оставит на
   доске задачу с чужим тегом — она выглядит занятой, хотя ею никто не занят.
7. **`blocked` требует причины.** `block` без внятного «что именно мешает и что для этого
   нужно» бесполезен: человек всё равно придёт спрашивать.
8. **Перенос из `done` снимает отметку выполнения** (серверная логика). Не гонять
   закрытую задачу по доске «посмотреть» — она перестанет быть закрытой.
9. **Колонки не двигать в обход скилла.** Команды перечитывают состояние после переноса и
   падают, если он не применился; прямой вызов API это не проверяет и молча врёт
   (`change-column` на системных колонках отвечает 200, ничего не сделав).
10. **Колонки не удалять.** Удаление осиротит стоящие в ней задачи — они пропадут с доски,
   оставшись в проекте.

Остальное:

- **Результат в `--report` — конкретный:** что изменено (файлы), чем проверено (результат,
  числа), хеш коммита. Не «сделано».
- **Записи в карточке помечаются:** `ПЛАН`, `РЕЗУЛЬТАТ`, `НА ПРОВЕРКУ`, `БЛОКЕР`,
  `ВОЗВРАТ В ОЧЕРЕДЬ` — плюс имя агента. По карточке видно, кто и на каком шаге что решил.
- **Нечёткую формулировку чинить, а не терпеть.** Заголовок карточки — то, по чему
  задачу находят и понимают; «разобраться с X» через неделю не значит ничего.
  `sing.py rename T-... "инфинитив + конкретика"` меняет только заголовок и
  подтверждает правку перечитыванием. Переформулировал чужую карточку — скажи об этом
  в `report`, иначе человек не поймёт, куда делась его.
- **Не выдумывать задачи.** Работаем только с тем, что в очереди. Найденное попутно —
  `sing.py add` в `todo`, а не молча чинить в текущей задаче.

## Кто взял задачу

Тег `agent:<имя>` вешается **каждой** командой, меняющей задачу — `start`, `report`,
`done`, `block`. Не только в `start`: задача, закрытая напрямую через `done`, иначе
осталась бы без следа о том, кто её сделал. Снимает тег только `release`.
Тег остаётся и после закрытия: это след, кто сделал.

**Имя определять не нужно — скилл узнаёт себя сам** по каталогу, из которого запущен:
`~/.claude/skills/…` → `claude`, `~/.codex/…` → `codex`, `~/.config/opencode/…` →
`opencode`, `~/.gemini/config/…` → `antigravity`, `~/.qwen/…` → `qwen`. Каждый
инструмент держит свою копию, поэтому признак детерминированный. Запуск не из каталога
скилла (из репозитория-эталона) опознаётся по метке сессии инструмента.

Порядок: `--agent` → `$SINGULARITY_AGENT` → поле `agent` в `singularity.json` →
определение по каталогу → `claude`. Явно заданное человеком идёт первым: догадка по
среде перебивать его не должна.

```bash
sing.py whoami                     # под каким тегом я работаю и откуда это имя
```

Не проси у человека `export SINGULARITY_AGENT` и не выставляй её сам без причины:
забытая переменная означала бы, что все агенты подписываются одинаково.

Теги в SingularityApp общие на аккаунт, не по проектам, поэтому префикс `agent:`
обязателен — он держит их вместе в общем списке. Читающие команды теги **не создают**:
`list --mine` для агента, который ещё ничего не брал, просто вернёт пусто.

`board` показывает держателя сам — колонкой `@имя` слева от задачи, до заголовка:
заголовки разной длины, и метка в хвосте строки вставала бы у каждой строки в своё
место. Несколько держателей — через запятую (это сигнал, что задачу ведут двое, а не
норма). Тегов на доске нет — нет и колонки: лишнего запроса `/tag` в этом случае не будет.
Отдельная команда, чтобы понять «занято ли и кем», больше не нужна.

## Декомпозиция

Крупную задачу разбивать до начала работы:

```bash
sing.py add "Подзадача" --parent T-... --column todo
sing.py checklist T-... "шаг 1" "шаг 2"
```

Подзадачи — отдельными карточками, если каждая имеет самостоятельный результат;
чек-лист — если это шаги внутри одной.

### Прогресс по чек-листу

Пункты **отмечаются по мере выполнения**, а не пачкой перед `done`: чек-лист для того и
нужен, чтобы по карточке было видно, где работа остановилась. Задача в `wip` с чек-листом
`0/5` не отличима от незапущенной.

```bash
sing.py checklist T-...                 # показать: нумерованный список и прогресс N/M
sing.py check T-... 2                   # отметить пункт №2 выполненным
sing.py check T-... "обновить доки"     # он же — по тексту
sing.py check T-... 1 3 CH-...          # несколько разом, ссылки можно смешивать
sing.py uncheck T-... 2                 # снять отметку (отметили не тот пункт)
```

**Сослаться на пункт можно тремя способами** — номером из вывода, текстом или `CH-`id:

- **номер** — основной для агента: чек-лист с номерами печатают `show`, `next` и
  `checklist`, то есть номер уже на руках и лишнего запроса за `CH-`id не нужно.
  Нумерация идёт по `parentOrder`, новые пункты дописываются в конец — номера уже
  существующих от этого не сдвигаются;
- **текст** — для человека, который смотрит в карточку и называет пункт словами.
  Точное совпадение заголовка бьёт совпадение по части: «Написать тесты» отметит именно
  его, а не «Написать тесты на пагинацию». Если под текст подходит больше одного пункта,
  команда **отказывается** и перечисляет кандидатов — отметить не тот пункт молча хуже,
  чем не отметить вовсе;
- **`CH-`id** — когда пункт уже известен точно (скрипт, разбор лога).

`check` и `uncheck` перечитывают чек-лист после записи и сверяют поле `done`: этот API
умеет ответить `200`, ничего не сделав. Не изменилось — команда падает, а не рапортует
об успехе.

Тег `agent:*` эти команды **не вешают** — в отличие от `start`/`report`/`done`/`block`.
Отметка пункта не меняет статус задачи; её ставят внутри задачи, уже взятой через `start`,
а тот тег уже повесил.

## Секции и заметки проекта

**Секции** (группы задач) режут проект по направлениям и не связаны с колонками: задача
одновременно лежит в секции и стоит в колонке. Полезно, когда очередь разрослась и агент
должен брать только своё направление.

```bash
sing.py groups                          # секции и сколько в каждой открытых
sing.py groups --create "Инфра"
sing.py add "Задача" --group "Инфра"    # секция должна существовать
sing.py add "Задача" --group "Доки" --new-group   # завести секцию заодно
sing.py next --group "Инфра"            # брать только из своего направления
```

**Заметки проекта** — долгоживущий контекст (соглашения, как разворачивается прод, чего
не трогать). Они лежат в проекте, но на канбан-доску не попадают и в очередь задач не
лезут, поэтому не мешают.

```bash
sing.py notes                                    # прочитать перед работой
sing.py notes --add "Контекст" --text "..."      # оставить контекст следующему агенту
```

**Читать `notes` до `start`**, если в проекте они есть: дешевле, чем выяснять
договорённости по факту сломанного прода.

## Что не делает

- Не удаляет проекты. Задачу удалить умеет в двух случаях, оба — уборка за собой:
  `rm --yes` (проверки идут на живом трекере, созданное для проверки удаляется в тот же
  заход; без подтверждения `rm` отказывает) и `doctor --write`, который убирает
  собственную пробную задачу, созданную секундой раньше.
- Не выходит за «ИИ проекты» — см. ограничение области выше. Просьбу «поработай с задачей
  из другого проекта» выполнять нельзя: нужно либо перенести проект под «ИИ проекты»
  руками, либо осознанно менять `ROOT_PROJECT_TITLE`.
- Не трогает чужие/расшаренные проекты: API отдаёт только личные.
- Не заменяет `JOURNAL.md`. Отчёт в карточке — про эту задачу; журнал — про решения,
  риски и изменения состояния системы.
- Не создаёт повторяющиеся задачи (не поддержано API).

## Диагностика

`sing.py doctor` — токен, привязка, живы ли колонки. Права **на запись** он не проверяет:
для этого `sing.py doctor --write` — создаёт в привязанном проекте пробную задачу,
проверяет запись по шагам (PATCH, перенос по колонкам с возвратом, чек-лист,
complete/uncomplete) и удаляет пробу в том же заходе, перечитывая состояние после каждого
шага. Код 1 — записи нет; строка `ПРОБА ОСТАЛАСЬ НА ДОСКЕ: T-…` — уборка не отработала,
задачу надо удалить руками. Типовое:

- `401` — токен отозван либо ему не хватает прав (права правятся только пересозданием токена).
- `КОЛОНКА ПРОПАЛА В ТРЕКЕРЕ` — id колонки в привязке есть, а в трекере такой колонки
  нет: удалили или пересоздали руками. Перезапустить `init --apply`.
- `НЕТ В ПРИВЯЗКЕ` (`doctor`) и `⚠ РОЛЕЙ БЕЗ КОЛОНКИ` (`board`) — это другое: роли нет в
  самом `singularity.json` (старая привязка или правка руками), колонка при этом может
  спокойно жить на доске. Чинится тем же `init --apply`. Пока роль не привязана, `board`
  печатает её пометкой без счётчика, а `start`/`next`/`list`/`move` по этой роли отказывают:
  задачи такой роли доска не показывает вовсе — не путать с «в колонке пусто».
- `Свободных задач нет` (код выхода 2) — очередь пуста, это нормальный исход, не ошибка.
- `⚠ ВНЕ КОЛОНОК` в выводе `board` — задача есть, а на доске её не видно. Две причины:
  завели в приложении мимо канбана, либо `add` оборвался между созданием задачи и привязкой
  к колонке. Лечится `move T-... <роль>`; `release` для этого не годится — он заодно снимает
  теги и отметку выполнения.
- `⚠ КОЛОНКИ МИМО ПРИВЯЗКИ` — на доске колонок больше, чем знает скилл. Обычно это
  раздвоение после `init` на неразвёрнутом канбане, разбор — `doctor`.
- Таймауты API — штатный режим, а не редкость. GET повторяются автоматически (3 попытки),
  привязка к колонке — тоже; `POST /task` не повторяется никогда, иначе будет второй объект.
  Сюда же — сервер, который принял соединение и не ответил: это такой же сетевой сбой
  («Сеть недоступна…»), а не особый случай.
- `⚠ установленные копии скилла разошлись с этим деревом` — это предупреждение печатают
  `start` и `done`, запущенные **внутри репозитория-эталона самого скилла**; в обычном
  рабочем репозитории его не бывает. Значит, копии скилла, по которым работают агенты, не
  совпадают с тем деревом, что перед глазами: либо правку не раскатали, либо база дерева
  устарела. Команду оно не роняет и раскатку не запускает. Разбираться так:
  `tools/install.sh --check` — что именно разошлось, дальше `tools/install.sh` из
  основного рабочего каталога (из git worktree раскатка отказывает намеренно: она затрёт
  общие каталоги пяти инструментов содержимым отдельной ветки). Отключить на один
  запуск — `SINGULARITY_NO_SYNC_CHECK=1`, но это про «сейчас не до того», а не про
  «проблемы нет».
- `⚠ GET …: сервер обещал N объектов, собрано M` — выборка неполная, и это не косметика:
  на неполной выборке `board` покажет заниженные счётчики, а `next`/`list` не увидят
  часть очереди. Числа из такого прогона использовать нельзя — повторить команду.

Счётчик в заголовке колонки `board` — это ВСЯ колонка, а не число показанных строк
(строки в `done` урезаются `--limit`, и тогда рядом стоит «показаны N»). Проверено на
проекте в 1150 задач: `board` даёт `850` и `300` по двум колонкам, что совпадает с
`pagination.total` сервера по каждой колонке.

**Формат поля проверяется по локальной базе приложения, а не по API.** API принимает и
отдаёт обратно то, что приложение разобрать не может (так было с `note`), поэтому круг
«записал через API → прочитал через API» этот класс ошибок не ловит в принципе. Перед
тем как писать поле в форме, которой раньше не писали, — посмотреть частотную картину
форм по живым данным: `tools/db-shapes.py` в репозитории-эталоне, процедура и найденные
расхождения — в `references/api.md`. База боевая: только чтение.

Справочник по API, формату заметок и подводным камням — `references/api.md`.
Инструкция для человека (установка, подключение репозитория, команды) — `README.md`.
